# XBAND サーバーコマンド仕様 下書き

開発終了時に統合する通信仕様の解析記録。対象は、対戦エリアとプレー時間の表示を更新するコマンド32、対戦エリアの設定項目を更新する4C、および端末が設定値を報告する1Cである。サーバーは4Cで設定項目を操作不可にできる。ROMには複数の選択肢をオフラインで切り替える処理があり、設定値の保存形式と送信形式も確認済みである。ユーザーの実画面試験でエリアの切り替えとプレー時間の表示を確認した。再起動後の選択値保持と時間外の接続拒否は別途操作確認が必要である。時間帯制限は今回のサーバーで判定する。当時のROM自身による曜日や時刻の制限判定は未解明である。

解析日 2026年10月7日。記載するコマンド番号、リソース番号、アドレス、バイト値は16進数。

## 旧サーバーを基準にする再現方針

サターン、SNES、16ビットSegaのXBANDは基本の仕組みが共通であるというユーザー指定の前提を採用し、各機能のサーバー側の動作は公開旧ソースを基準に調整する。機種別資料がないことだけを理由に、共通の待機・マッチング・メール・結果処理を独自設計に置き換えない。この前提は移植方針であり、全機種の通信バイト列が一致するという確認結果ではない。

待機登録、相手選定、発着信役割、メールの保管、アカウントとランクの管理は共通ロジックとして扱う。コマンド番号、フィールド長、文字コード、通知本文、ROM内の資源番号は機種別の変換処理に分け、サターンROMで確認済みの形式を使う。日本の局番や曜日表示などのローカライズは、旧米国版の値をそのままコピーしない。ROMと旧ソースの挙動が明確に異なる場合は、差分を仕様に残して対象ROMに合わせる。

仕様の状態は「旧ソースで確認した動作」「共通として採用した仕様」「サターンROMで確認済み」「運用上の拡張」「未解明」を区別する。旧ソースのコメントだけにある予定、未実装処理、仮データ、既知の不具合を完成した当時の仕様とは扱わない。独自のゲーム内通知は追加せず、通知が必要な結果については対象ROMの既存の応答と本文を対応付ける。

既存の運用設定は維持する。全端末共通の可変待ち時間、ゲーム別の勝者・敗者ポイント、ランク条件の編集、履歴表示は再現仕様とは別の拡張として明示する。固定テスト値の配信は復活させない。メールの応答準備を受信完了と断定せず、ROMからの再送を独自に代行しないという従来の指定も維持する。今回、ポイントとレベルの調整値は変更しない。

### 共通機能の差分と調整順

| 項目 | 現行実装と旧ソースの差分 | 対応状態 |
| --- | --- | --- |
| 指名先の探索 | 指名先ではない別ユーザーのゲーム不一致でもエラーにしていた | 指名先に一致した場合だけゲーム不一致を判定するよう共通処理を修正 |
| 指名対戦の受付設定 | ROMの「はい／いいえ」と送信0Bのフラグを特定し、アクセス履歴へ申告値を記録。相手判定への適用は未実装 | 先に待機している拒否相手への指名要求と、後から接続する拒否相手の自動要求を区別し、サターンの返信へ対応付ける |
| 対戦エリア | 現行は選択値を設定画面と使用状況へ反映するが、地域による候補除外は未実装 | 旧ソースの発信側の通話範囲判定を、日本の局番の意味へ対応付ける |
| 待機期限 | 現行のペア制御はROMの終了通知を受け、共通登録クラスへ無期限相当の期限を渡す。旧ソースはサーバー上の登録時刻と発信猶予も使う | ROMの時計とサーバーの時計を区別した期限管理が必要 |
| メールの受信容量 | 旧ソースは端末申告の受信箱件数を使い、入らないメールをサーバーに残す | v49で固定4件バッチを廃止。共通サターンROMの8件上限と接続ユーザーの申告件数から空きを計算。サーバー保管総数は無制限方針を維持 |
| アカウントとランク | 旧ソースは端末IDとユーザー枠の識別を使い、ゲーム別のランク表から表示を作る | v49メールは申告端末ID＋0～3枠を識別。未登録IDは正規化した電話番号へフォールバック。名前変更は当該枠のみ更新。認証やポイント台帳の識別変更は対象外 |

旧Matching_SpecificはMatching_FindMyChallengeeで指名先を探索し、見つからなければ待機登録へ進む。ゲーム不一致、他ユーザーを指名中、指名受付拒否は、指名先が見つかった後に判定する。自動対戦も、指名受付が許可されている場合には自分を指名した待機者を先に確認し、通常のゲーム別キューへ進む。[旧マッチング処理](https://github.com/X-Band/SegaServer/blob/d35c96e0c0322f9a319840294987cdc745bbd126/ServerDataBase/Matching_Matching.c)

最初の修正はpb3_pair_control.hppのregisterStandbyに適用した。左右、4ユーザー枠、8対応ゲームID、3待ち時間の既存192ケースに加え、指名先ではないユーザーが別ゲームで待機する384ケースを、登録順序の両方で確認した。修正前には同じ回帰試験がゲーム不一致の例外で失敗し、修正後は正常な1C・0E・02の再応答、待機チケットと指名先の保持、後からの本来の指名先との組み合わせが成立した。保存した要求の再生とサーバー制御の試験であり、実画面操作や当時のサターンサーバー応答の捕捉ではない。

旧Server_SendMailは利用者の識別と受信箱の申告を使い、容量超過分をサーバー側に残す。旧Server_BuildRankingはゲーム別のしきい値と累積ポイントから現在ランク、次のランク、必要な差分を作る。この構造を基準とし、サターンの数値や日本語ランク名、メール形式は対象ROMへ合わせる。[旧メール配送](https://github.com/X-Band/SegaServer/blob/d35c96e0c0322f9a319840294987cdc745bbd126/Server/Send/Server_SendMail.c)、[旧ランク表示作成](https://github.com/X-Band/SegaServer/blob/d35c96e0c0322f9a319840294987cdc745bbd126/Server/Send/Server_SendRanking.c)

## 4ユーザーと受信箱の容量（v49）

旧ソースの `Server_SendMail` は接続したユーザーの `numMailsInBox` と `kMaxInBoxEntries` から空きを計算し、容量超過分をサーバーに残す。旧SegaOSの `Mail.h` では上限10件だが、この数値をサターンへ流用しない。

共通サターンROMでは、`00270001` の登録先 `060473D0` が選択ユーザーの受信箱件数を取得して最大8件に制限する。`0027000A` → `06047230` は選択ユーザー0～3へ `0136` を加え、受信箱のリソースタイプ `0136`～`0139` を選ぶ。`0602C964`～`0602C99E` はこの件数と、各メールのオフセット54の2バイト値を0Bへ申告する。現在の要求パーサーは16件までの構造を受け入れるが、配送側では8件以上の申告を空き0として扱う。同じ申告値が複数あってもメール件数を重複排除しない。

v49の通常ジャーナル配送は、一応答固定4件を廃止し、`max(0, 8 - 申告件数)` 件まで、古い保管順に返信へ格納する。入りきらないメールは未配送のまま保管し、次のROMのサービス要求で再評価する。メール専用・自動対戦・指名対戦の共通配送に適用する。サーバーの保管総数や共有送信箱の投稿件数を8件へ制限しない。サーバー側の自動再送、独自のゲーム内満杯通知、既読・配達完了の判定は追加しない。応答へ格納したものを再提示しない従来の指定を維持し、実受信完了とは区別する。

ユーザーの識別には0Bのプロフィール先頭の申告8バイトIDとユーザー枠0～3を使う。未登録の全FF・全0のIDには、従来互換の正規化電話番号を端末キーとして使う。このフォールバックは旧サーバーの正式なID割り当てや認証を再現したものではない。0Bヘッダーのオフセット06にある2ワードは時刻由来の値であり、端末IDとして使わない。登録されたIDがある場合は、電話番号変更や表示名変更でユーザー枠を別アカウントへ変更しない。

メール受信は接続ユーザーのみとし、他の3ユーザーの受信箱へ一括配送しない。一方、端末送信1Dの共有送信箱には4枠のメールが混在するため、各レコードの送信者枠を使う。選択ユーザー名を他枠の送信者名へ流用しない。名前変更はその枠だけ更新し、旧実装にあった「一枠の不一致で全宛先を解決不可にする」挙動を廃止した。同名宛先が複数存在する場合は曖昧な配送を保留する。新規投稿で既知の送信者名と宛先アカウントは保存時に固定し、後の名前変更で過去メールを別ユーザーへ付け替えない。旧履歴にはこれらのメタデータがないため、元ファイルを変更せず従来形式で読み、未特定の枠・宛先は引き続き保留する。

メール履歴の詳細とサーバーログに、宛先の直近の受信箱申告・返信格納件数・配送可能なサーバー残件数を表示する。未特定の送信者や宛先の保留分はこの残件数に含めない。これらはアクセス時の観測値であり、再起動後は次のアクセスまで表示しない。既存履歴ファイル、ユーザー保存データ、ポイント台帳は変更しない。

元ROMの件数取得を4ユーザー×0～16件の68ケースで隔離実行し、リソースタイプの分離と8件への制限を確認した。選択ユーザーとリソース件数のバックエンドは代替している。ジャーナル試験は2端末×4ユーザーの96件保管、56通りの申告件数、容量超過保留と再起動、名前変更、同名保留、登録IDでの電話番号変更、メール専用・自動・指名の要求を確認する。これは保存要求の再生と隔離試験であり、今回の変更後の実画面受信やフラッシュ保存の確認ではない。

## コマンド4C 対戦エリア設定項目の更新

方向はサーバーから端末。共通XBANDプログラムは、設定画面用リソース `0200:0022` を置き換える。

| フィールド | 長さ | 内容 |
| --- | --- | --- |
| コマンド | 1バイト | `4C` |
| 本文長 | 4バイト | ビッグエンディアン。後続の操作可否と文字列領域の合計バイト数 |
| 操作可否 | 2バイト | ビッグエンディアン。`0000` は操作不可。`0001` で有効になることを隔離テストで確認 |
| 文字列領域 | 可変 | EUC-JP、各文字列を `00` で終端。項目名に続き、選択肢名と説明文の組を並べる |

概略は `4C [本文長 u32 BE] [操作可否 u16 BE] [文字列領域]`。操作可否は選択中のエリアや選択肢数ではない。ROMのコンストラクターは、この値がゼロかどうかを判定してウィジェットの有効状態を決める。`0001` 以外の非ゼロ値を正規仕様として採用する根拠はない。

任意選択用の候補文字列は次の順序とする。

1. 対戦エリア:
2. 同一局番内
3. 市外へのコールはしません
4. 全国
5. 長距離通話になる可能性があります。

「同一局番内」とその説明は元のDRAMDBリソースにも存在する。「全国」とその説明はユーザー提供の当時の操作画面で確認できる。両方を並べた候補データは元の受信処理に受け付けられた。これは当時のサーバーが送ったバイト列を捕捉した記録ではない。

### 現在の固定表示との違い

`usageAreaSettingWire()` の固定モードは操作可否を `0000` とし、全国または同一局番内の一方だけを送る。任意選択モードは操作可否を `0001` とし、上記の二択と説明文を送る。グレーアウト解除だけでは選択肢は増えないため、両方の選択肢を含むリソースへの更新が必要になる。元のDRAMDBの設定項目も、操作不可で同一局番内の一択である。

サーバーの上書きを解除して返信から4Cを省くだけでは、すでに置き換わった設定リソースが元に戻るとは限らない。任意選択への移行では、操作可能な二択のリソースを明示的に渡す必要がある。以後の接続で全国固定のデータを再送しないことも必要になる。

v44のサーバー設定画面では、登録電話番号ごとに次のモードを保存できる。既存設定はそのまま読み込み、任意選択へ自動移行しない。

| メニュー | JSONのselection | 設定項目の返信 |
| --- | --- | --- |
| 上書きしない | -1 | 4Cを送らない。端末に保存済みの項目は残る |
| 同一局番内に固定 | 0 | 操作不可の一択 |
| 全国に固定 | 1 | 操作不可の一択 |
| ROMで任意選択 | 2 | 操作可能な二択。同一局番内が0、全国が1 |

任意選択モードで配信するのは画面項目であり、4ユーザーの変数0049は上書きしない。指名・自動対戦のサービス返信では、端末送信1Cに載った選択中ユーザーの値が0または1なら、使用状況の表示文字列0052をその値に合わせる。値が取得できない、または二択外の値なら0052は上書きしない。ゲームIDを取得できた返信では、二択の4Cを配信する。オフラインの選択直後に使用状況の表示も変わることは、このサーバー処理では保証しない。表示の同期は次の対象サービス返信で行う。

時間帯制限と二行表示の設定は、対戦エリアのモードと独立して保持する。任意選択モードは地域による対戦相手の絞り込みや電話ルーティングを変更しない。今回の二択の順序は元ROMで検証したローカル実装の順序であり、当時のサーバー配信順序を復元したものではない。

### ROM内の処理

対象の `XBAND.BIN` は740960バイト、SHA-256は `49ec092d5d109e84540e556103bde534214aee446b57fd89f42a35d0e1e447f3`。アドレスはこのバイナリーを `06006000` にロードした場合のもの。

| 処理 | アドレス等 | 確認内容 |
| --- | --- | --- |
| コマンド登録 | `0602F832`、`0602F88C` | オペコード4Cを受信処理に登録 |
| 受信処理 | `0602DAB8` | 本文長、操作可否、文字列を読み、設定リソースを構成 |
| リソース書き込み | セレクター `00050018` | タイプ0200、ID0022。受信した操作可否をヘッダーのオフセット12に格納 |
| コンストラクター | `060379A4` | ヘッダー12が非ゼロなら、ウィジェット32の有効状態を1にする。選択肢数は文字列数から計算 |
| 描画処理 | `06037DF8` | ウィジェット32が0の場合、通常色の代わりに灰色 `294A` を選択 |
| 入力処理 | `0603800C` | 入力ビット80で次、40で前へ切り替え。選択肢の端で折り返す |
| 選択値の取得 | `06037D7C`、プロパティ13 | ウィジェット30にある選択インデックスを取得 |

「サーバーが操作不可を指定する」とは、4Cの2バイト値をゼロで送ることを指す。操作のたびにサーバーへ許可を問い合わせる仕組みではない。入力処理自身にはネットワーク要求はない。画面生成と終了処理から、初期値の取得と変更値の書き込み要求へ至る経路は確認済みである。実際のコントローラーによる一連の操作、永続保存、接続時のアップロードは別途確認が必要である。

設定画面の初期化処理 `0605D15C`（セレクター `00290010`）は、選択ユーザーを `00280008` で取得し、設定項目0022、0021、0023へユーザー別の選択インデックスを設定する。変数の読み出しは `00120001`、ウィジェットへの設定は `001E0003` のプロパティ0013を使う。対戦エリアは変数0049の32ビット値をユーザー番号×8ビット右へシフトした最下位ビット、指名対戦受付は変数0025をユーザー番号＋4ビット右へシフトした最下位ビットから取得する。待ち時間は変数 `004A + ユーザー番号` を参照する。ユーザー番号は0～3である。元リソース0200:0021の選択順は「はい」が0、「いいえ」が1であり、受付の許可を表す真偽値とは逆になる。4Cの操作可否は、この保存値の読み出しとは別である。

元ROMの初期化処理とシフト処理を実行する隔離テストで、4ユーザー×4種類のビットパターン×3種類の待ち時間、計48ケースを確認した。変数データベースと画面部品のバックエンドは代替したため、確認対象は初期値の取得と設定に限る。変更値の保存、再起動後の保持、接続要求への反映、地域別マッチングはこのテストでは確認していない。二択の候補データでは0を同一局番内、1を全国としたが、当時のサーバーによる選択肢の順序までは確認していない。

変更値をまとめる処理 `0609914C`（登録セレクター `00450004`）も確認した。項目0022、0021、0023のプロパティ0013を `001E0004` で読み出し、既存の変数0049、0025と合成する。変数0049では選択ユーザーの1バイト全体を選択インデックスで置き換える。単に最下位ビットだけを更新する処理ではない。変数0025ではユーザー番号＋4の1ビットだけを置き換える。他の3ユーザーのエリア用バイトと、他の指名受付用ビットは保持する。待ち時間と合わせ、変数ID `0049`、`0025`、`004A + ユーザー番号` の3件を `00120003` へ渡す。

元ROMの合成処理、左シフト処理、一括書き込み処理 `060125B0` を実行し、4ユーザー×4種類の既存値×エリア2択×指名受付2択×待ち時間3択、計192ケースで `00120002` への3件の書き込み要求と他ユーザーの値の保持を確認した。画面部品の取得と単一変数の書き込み先は代替している。実際の変数データベースやフラッシュへの保存、接続時のアップロードは未確認である。

設定画面のリソース `0202:0009` は、オフセット08に終了時の処理番号 `00000003`、オフセット10に初期化の処理番号 `0000000F` を持つ。画面生成処理 `0603B870` は前者を画面オブジェクトのオフセット24へコピーし、後者に1を加えて `00290010` を呼ぶ。画面終了処理 `0603BB20` はオブジェクト24の値に1を加えて `00450004` を呼ぶ。いずれも画面オブジェクトを引数として渡すため、初期化・保存処理が同じ画面の設定項目を参照できる。主な子ウィジェットの解放は書き込み要求の後に行う。

### 設定変数の保存形式

## 指名相手が未待機の場合のROM待機

サーバーv48では、指名先の待機登録がない場合も、サービス返信を保留し続けず、受信待機の1C、待機期限の0E、正常終了の02を返す。指名待機にはコマンド22の独自通知文を追加せず、通知0062をサーバーから強制登録することもしない。期限は全端末共通の待ち時間設定とROM申告のみじかい・ふつう・ながいから決める。タイマー開始、経過判定、待機終了通知はROMの元の命令で処理する。

待機終了時の本文は元の文字列 `0105:0062` の「あなたにふさわしい対戦相手を見つけることができませんでした。度数は引かれていません。もう一度、対戦を申し込んでください。」である。この本文を変更しない。ROMの終了・取消を読み取り専用の監視が検出すると、サーバーは現在のチケットの待機登録を解除する。期限終了を対戦結果とは扱わず、ポイント付与の根拠にしない。

指名先はサーバーの待機登録に保持する。同じゲームの別ユーザーが接続しても、自動対戦へ読み替えて組み合わせない。指名先が後から接続した場合は、ROMの待機準備完了を確認してから通常の対戦経路へ進める。再申し込みには新しいチケットを使い、以前の取消通知で新しい待機を消さない。接続世代の更新では指名先も初期化する。名前の照合はローカル端末の申告に基づくものであり、利用者認証ではない。

「指名先の登録がなければROM待機へ移す」という対応は、今回ユーザーが指定したサーバー動作であり、当時のサーバーの未待機応答が捕捉できた結果ではない。ROMの0E受信、期限比較、終了通知0062、既存本文の表示データ構築は隔離試験で確認している。実要求1377バイトの再生から派生した192ケースでは左右、4ユーザー枠、8ゲームID、3待ち時間について、1C・0E・02、独自通知なし、指名先保持、別ユーザー排除、後からの接続、取消・再申し込みを確認した。ROM試験の時計・通信・画面バックエンドには代替処理を使っている。ユーザーの実画面試験では待機期限終了の既存本文を確認した。同じ実行のログには、待機準備完了の通知1回と、ROM時計が開始値2010と期間14400の合計に達した後の取消通知1回があり、サーバーは同じ待機チケットを解除している。従来の自動対戦の待機開始通知と、利用時間外の拒否処理はこの変更の対象外とする。

### サービス接続を保持する場合の受信処理

現在のv48は1C・0E・02でサービス通信を終了してから着信待機へ進む。この実装を当時の接続方式の証明とは扱わない。接続中のままマッチングを待つ方式を採るには、02を保留した間の受信処理と、接続中の期限通知、相手成立後の回線移行を成立させる必要がある。

## コマンド0D 受信処理の登録解除

方向はサーバーから端末。形式は `0D [受信コマンド番号 u16 BE]`。受信処理 `0602B108` は2バイト値を読み、指定した受信コマンドの処理先を0に置き換える。曜日、開始時刻、終了時刻を保存するコマンドではない。時間外拒否を実装する目的で送らない。

呼び出しは `0602F258` から内部セレクター `002A0006`、登録ラッパー `0602FAC0`、`0602FF04` を通り、内部セレクター `00000002` の登録処理 `0600D8B8` に到達する。登録グループは受信処理の2Cであり、処理先ポインターは0である。`0602F258` に渡る最初の引数0は、後続のラッパーでグループ番号2Cに置き換わる。この0を接続許可や時間制限の状態値と解釈しない。

隔離テスト14ケースでは、受信コマンド番号7通りと読取成功・失敗を組み合わせた。元の受信処理、ラッパー、登録処理を実行し、成功時は指定した登録先一件だけが0になること、失敗時は登録表を変更せずFED2を返すことを確認した。スタック、読取状態、対象の登録先以外の隔離RAMも変わらなかった。試験のストリームと内部呼び出しの振り分け、登録表の初期状態は合成データである。

これは処理先の解除までの確認であり、解除後に同じコマンドを受信した際の全体動作、登録可能な番号の全範囲、解除を利用した当時の用途を確定するものではない。サターン版の曜日・時間帯制限用の専用応答は引き続き未確定である。

## コマンド22と02による通知とサービス終了

時間外拒否の候補応答として、任意の説明を通知する22と、サービス返信を終える02を組み合わせる経路を確認した。22自体は時間外専用でも接続拒否専用でもない。曜日別の条件を判定するコマンドではなく、説明の通知登録を行う。対戦を許可しない場合、サーバー側では相手番号や待機開始の応答を送らず、通知してサービスを終了する方式を採れる。ただし、この組み合わせが当時の時間外拒否に使われたことを示す通信記録はない。

22の本文は、順に2バイト値を四つ、本文長の4バイト値、終端00付きの文字列を持つ。第1値は通知処理へ渡す値、第3値と第4値は表示時間の最小値と最大値に対応する。旧ソースでは第2値はダイアログのテンプレートIDだが、サターンの受信処理 `0602BAEC` はこれを読んだ後、この通知登録経路では使用しない。試験で0000と4321を送っても登録結果は変わらなかった。任意のIDを正規仕様として認めた結果ではなく、現在のサーバーは0000を維持する。[旧サーバーの通知送信](https://github.com/X-Band/SegaServer/blob/d35c96e0c0322f9a319840294987cdc745bbd126/Server/Send/Server_SendDialog.c)

通知登録 `06093474` はリソースタイプ0124の一時レコードを作る。オフセット00には第1値、02には最小表示時間、04には最大表示時間、06にはFFFF、08には選択ユーザーのインデックス、09以降には文字列を格納する。22の受信処理は正常時に0を返すため、次のコマンドの読み出しが続く。第1値を0001と0010に変えた試験では値がそのまま保存された。通常のメニュー処理で0001を表示対象にする条件は、後述の表示処理で確認している。

02の受信処理 `0602C768` は02を返信し、内部呼び出し `002D0006` に負の1を渡してから、終了を示すFED3を返す。受信ループ `0602FADC` はこれを一般エラーとは区別する。上位のサービス処理 `06029FF2` から `0602A014` はFED3を正常終了へ変換し、戻り値を0にしてイベント63のコールバックを呼ぶ。ここで通信エラーを発生させることが接続拒否の仕組みなのではない。

隔離テスト24ケースは、合成ASCII本文と現行サーバーの日本語本文、通知フラグ2通り、第2値2通り、読取結果3通りを組み合わせた。正常系8ケースでは、元のコマンドデコーダー、通知受信、通知レコード構築、02受信、正常終了分岐を続けて実行した。本文と時間値の保存、02の返信、イベント63、最終戻り値0を確認した。ヘッダーまたは本文で持続する読取失敗を模擬した異常系16ケースでは、通知登録や正常終了コールバックを行わず、FED2を返した。単発の失敗後に同じヘッダーの読み出しが復旧する場合を試した結果ではない。

正常終了後は、受信処理が作った同じ0124レコードを元の通知表示処理へ渡した。通知停止と接続中状態を解除した通常メニュー状態、表示マスク0001、受信時と同じ選択ユーザーを試験条件として与えた。フラグ0001の4ケースはダイアログ呼び出しに到達し、本文と最小・最大表示時間が入力データに一致し、通知の削除要求が出た。0010の4ケースは表示対象外で、削除要求も出なかった。日本語本文、フラグ0001、第2値0000の成功ケースでは、現行の `usageTimeDeniedNotice()` が生成する返信バイト列を変更せずに使用している。

試験のストリーム、メモリー割り当て、データベース保存、通信後処理、画面コールバックとUIの実体は隔離用の代替処理である。日本語のEUC-JPバイト列が表示用データまで保たれることを確認した結果であり、文字の描画、実画面での通知操作、接続終了から通常メニューへ戻る状態遷移全体の確認ではない。過去の待機タイマーが残っている場合の解除も、この試験の確認範囲には含めない。

旧サーバーの対戦開始処理には、`disallowGameConnect` が真の場合、マッチングを行わず正常戻り値を返す分岐が存在する。これは通知と対戦禁止の判断が別であることを支持するが、16ビットSega版の実装であり、サターンの時間外拒否そのものの証明にはならない。[旧サーバーの対戦開始処理](https://github.com/X-Band/SegaServer/blob/d35c96e0c0322f9a319840294987cdc745bbd126/Server/Server_StartGamePlay.c)

## 通知を表示する条件

通知表示処理 `06093670` は0124のレコードを選び、ダイアログの入力データを構築して、内部呼び出し `00470003` に渡す。通知の受信と実画面への表示は別段階である。通常のメニュー処理 `060099C8` は各ループの先頭で `0600A22C` を表示マスク0001で呼び出す。この経路では、現在のサーバーが使う通知フラグ0001が表示対象になる。

| 条件 | ROMの処理 |
| --- | --- |
| 全体の通知停止フラグ `060BA43C` が非0 | 表示処理を終了する。レコードは削除しない |
| 状態バイト `060B917A` が非0 | レコードの表示を延期する。取得は `002D001B`、設定は `002D001C` |
| 通知フラグに0002ビットがない | 呼び出しの表示マスクとの共通ビットが必要 |
| 同じく0002ビットがない | レコードのユーザーインデックスと現在選択ユーザーの一致が必要 |
| 通知フラグに0002ビットがある | 表示マスクとユーザーの照合を省略する。ただし全体停止と状態バイトの条件は残る |
| ダイアログ呼び出しが戻る | 一時メモリーとレコード参照を解放し、表示した通知レコードの削除を要求する |

0001だけを指定した通知は、受信時の選択ユーザーに属する。他のユーザーへ切り替えたままでは、そのユーザー向け通知はこの経路で表示されない。0002ビットはユーザー照合まで省略するため、表示を早める目的だけで置き換えると別ユーザーの通知を表示し得る。0010だけを指定したレコードは、表示マスク0001の通常メニュー経路では対象外となる。0010を渡す実際の呼び出し元や歴史的な各ビット名までは、この結果から確定しない。

文字列を直接持つレコードでは、ダイアログ先頭の二つの2バイト値へ最小時間と最大時間をコピーし、オフセット20以降に終端00付き本文を置く。ダイアログ呼び出しの戻り値は、この削除分岐では検査しない。表示した一件の削除要求後に処理を終了する。表示条件が一致しなかったレコードは参照だけを解放し、削除せず次のレコードへ進む。

文字列を直接持たないレコードでは、オフセット06のIDを内部呼び出し `00390006` に渡す。登録先は `06012B98` で、文字列タイプ0105を指定して `06012ED4` からデータベース取得 `00050014` を呼ぶ。ここで取得するのはダイアログタイプ0118ではない。取得に成功すると、文字列から表示用データを作り、文字列参照を解放してから表示する。文字列が見つからない場合は表示せず、通知レコードを削除しない。

VF Remixの元のDRAMDBには、`0105:0062` に対戦相手を見つけられなかった旨の本文があり、`0105:004F` は存在しない。一方、`0118:004F` には「時間切れ・長電話」のダイアログがある。通知レコードのIDに004Fを入れるだけでは、後者を呼び出さない。サーバー等が後から0105:004Fを作る可能性まで否定するものではなく、0118:004Fの発火条件と当時の時間外応答は未解明のままである。

隔離テスト1,440ケースでは、直接本文、元の0105:0062の日本語本文、存在しない0105:004Fの3通りに対し、通知フラグ5通り、表示マスク3通り、所有ユーザー4通り、全体停止と状態バイトの各2通り、UI戻り値2通りを組み合わせた。直接本文と0062の各76ケース、計152ケースがダイアログ呼び出しとレコード削除要求まで到達した。004Fの取得を試みた76ケースは表示せず、削除要求も出なかった。元の文字列取得ラッパーが0105を指定すること、選択条件、状態取得、本文と時間値のコピー、参照解放と削除の呼び出しを確認した。データベース・割り当て・UIの実体は代替処理であり、描画やユーザー操作の完了を確認した結果ではない。

## サービス接続前の対戦待機解除

対戦のサービス接続呼び出し経路 `06096438` では、接続前に `003F0007` で待機の有効状態を調べる。有効なら監視停止を呼び、`003F0003` の解除処理 `06094344` を実行する。解除処理は有効状態の2バイト値 `060BA5B4` を0にし、タイマー管理 `00250004` に `060BA5C4` を渡して取消しを要求する。開始値 `060BA5B8` と期限 `060BA5BC` の数値は、この解除処理では消さない。数値が残っていることだけでは、待機が有効とは判断できない。

サービスから正常値0で戻ると、`06096518` から `0609669A` へ進む。新たな待機開始指示0Eがなければ、接続後の `003F0007` は無効を返すため、受信待機の表示65と監視開始 `0053000B` へ進まない。正常戻り値そのものが待機を再開するわけではない。

隔離テスト8ケースは、以前の待機が有効か無効か、方向バイト0か1か、古い期限値2通りを組み合わせた。元の接続前分岐、解除処理、接続後の正常分岐を実行し、待機が有効だった場合だけサービス前に取消し要求が出ること、正常応答後に待機表示と監視を開始しないことを確認した。サービスの実体は「0Eなしで正常終了する」代替処理であり、22と02の受信ループを同じ試験内で連結した結果ではない。22と02が正常戻り値0を作ることは別の受信ループ試験で確認している。タイマー管理と通信・UIの実体も代替処理である。

この結果は当該接続経路の確認であり、全接続経路や起動時の保存状態の検証ではない。また、サーバー上の待機登録は別に解除する必要があり、ROMの有効状態だけでサーバー側の待機を判断しない。当時の曜日・時間帯制限を伝える専用応答は引き続き未確定である。

## サーバーで追加した時間帯制限

「使用状況と利用時間の設定」は、登録電話番号ごとに平日と土日の利用ルールを保持する。同じ端末の4ユーザーと全ゲームには同じ電話番号のルールを適用する。これはROMから解読した当時の制限仕様ではなく、今回追加したサーバー側の仕様である。

各ルールは「終日利用可能」「時間帯を指定」「利用不可」から選ぶ。時刻は日本時間、分単位とし、開始を含み終了を含まない。終了24:00を指定できる。開始が終了より遅い時間帯は翌日にまたがる。例えば金曜日22:00から02:00は、土曜日の利用ルールが利用不可でも土曜日02:00直前まで有効となる。

制限対象は「対戦接続のみ」または「対戦とメール」で選ぶ。初期状態では制限を有効にせず、従来の動作を保持する。有効にした場合、使用状況画面の二行は設定ルールから生成する。表示だけを任意文字列に変更する機能もあるが、表示だけの設定は接続許可を変更しない。

時間外の指名・自動対戦要求は待機登録前に拒否する。指名先も判定対象とする。待機中に時間外となった場合は待機を解除し、相手との回線接続が成立する前にも双方を判定する。すでに成立している対戦は強制切断しない。結果報告は受け付ける。メールを制限対象にした場合、拒否した要求から送信メールを登録せず、受信応答にも載せず、ROMの送信箱を消す応答を送らない。

拒否時は使用状況の表示更新に続き、既存のメニュー通知形式 `22 0001 0000 0078 012C [文字列長 u32 BE] [EUC-JP文字列と00] 02` を使う。自身の制限では「現在は利用時間外です。使用状況をご確認ください。」、指名先の制限では「指名した相手は利用時間外です。時間をおいてお申し込みください。」を通知する。これは今回のサーバーが選んだ通知形式であり、当時の時間帯制限応答を捕捉したものではない。アクセス履歴には「時間帯制限・接続拒否」または「時間帯制限・待機終了」を記録し、接続拒否の詳細では自身と指名先を区別する。

初回の許可判定から待機登録までの間に時間帯が終了した場合も、専用の拒否例外をサービス応答へ変換し、22と02で正常終了する。この境界では既に要求の観測履歴が保存されている場合があるが、受信メールの準備やROM送信箱の消去は行わない。通常の通信エラーや不正な要求を時間外拒否へ変換することはしない。

設定は既存の `usage-area-settings.json` に任意の `play_time` と `schedule` を追加して保存する。以前の設定ファイルも読み込める。変更は保存時に確定する。「時間帯制限を有効にする」にチェックし、曜日別の条件を指定して保存する。設定画面は保存済みの有効・無効、対象、時間帯を明示する。表示文言を指定するだけでは接続を制限しない。

通常の表示更新は次回の対戦サービス返信で行い、メール専用接続では行わない。接続許可は保存直後からサーバーの現在の設定で判定するため、ROMへ表示が反映される前に制限が適用される場合がある。時間帯や現在稼働中の設定ファイルを自動変更せず、次回の起動スクリプトはv48を使用する。

## サーバー共通の対戦待ち時間

サーバーの「対戦待ち時間設定」は、ROMで選ぶ三種類の待ち時間を全電話番号・全ユーザーID・全ゲーム共通で指定する。個別番号やIDの設定は持たない。ROMはユーザーごとの選択インデックスを送信し、サーバーがそのインデックスを共通の時間へ変換する。

| ROMの選択インデックス | 項目 | 初期値 |
| --- | --- | --- |
| 0 | みじかい | 1分 |
| 1 | ふつう | 2分 |
| 2 | ながい | 4分 |

各項目は1〜60分のプルダウンで変更でき、「みじかい ≤ ふつう ≤ ながい」とする。同じ値も許可する。初期値は以前の6000カウンター単位を基に分単位へ切り上げたローカル設定を維持するもので、当時の全サービスでこの値だったという意味ではない。設定ファイルがない場合もこの初期値を使う。

受信待機側へ送るコマンド0Eの値は、指定した分数×3600とする。自動対戦では同じ値からコマンド22の「約○分間探します」の通知文を生成する。指名待機にはこの22を送らない。期限はROMの60Hzカウンターで進み、エミュレーターの停止や実行速度の影響を受ける。日本時間の曜日別接続制限とは別の判定である。発信側とメール専用接続へこの待機通知を送ることはしない。

一件の申し込みで最初に待ち時間を読み出した値を、そのサービス接続の終了まで保持する。相手待ちで返信を繰り返し判定している間に保存しても、その申し込みの期限と通知文を変更しない。新しい申し込みから保存値を使い、既にROMが開始した待機の期限も変更しない。

設定は `standby-wait-settings.json` の `schema: 1`、`scope: server-global`、`minutes.short`、`minutes.normal`、`minutes.long` に保存する。環境変数 `XBAND_STANDBY_WAIT_FILE` で保存先を指定できる。保存前に範囲と順序を検証し、既存ファイルのバックアップと置換を行う。起動スクリプトは保存済みの共通設定を新しい試験用コピーへ引き継ぐ。ROMの選択値を書き換える処理ではない。

隔離テストでは保存・再読み込み・不正な数値の拒否を確認し、保存済みの指名と自動要求から作った診断用入力384通り（左右、4ユーザー、8ゲームID、3選択値）で0Eの期限が設定値に一致することを検証した。自動対戦の22通知文は同じ値を使い、指名待機には22を付けない。返信保留中の保存で既存要求の時間が変わらないことと、次の要求から新しい値を使うことも確認した。元ROMの受信処理では60分相当を含む0Eの12ケース、通知文の24ケースを実行した。通信・時計・画面の一部は代替処理であり、60分の実時間待機や全タイトルの実画面試験を完了した意味ではない。設定画面はプルダウン、保存、初期値表示、再表示、配置をネイティブ画面の隔離試験で確認した。

## 勝者と敗者のポイント設定

サーバーのゲーム設定で、ゲーム別の勝者ポイントと敗者ポイントをそれぞれ0〜999に設定する。電話番号・ユーザーIDによる配点の違いは設けない。既存ファイルの `win_points` は維持し、追加した `lose_points` がない場合は0とする。勝者ポイントが未設定の `-1`（上書きなし）なら、両者ともサーバーでは加算しない。引き分けの加算は0。当時の配点を復元したものではなく、今後の調査に合わせて変更できるローカルサーバーの設定である。

コマンド32で更新する文字列00B4と00B5は、自分と相手の勝利時の価値を表示するリソースであり、勝者用・敗者用の二つの付与先ではない。両方には従来通り勝者の値を送る。敗者ポイントを00B5へ送る変更は行わない。元の共通ROMで確認した加算経路は、勝者のみへの加算であり、今回の敗者加算はサーバーの結果集計と累積配信で扱う。

サービス応答の最初の準備時に勝者・敗者の設定と送信文字列を一緒に保持する。保存で値を変更しても、そのサービス要求の返信や結果集計には新しい値を混ぜない。履歴の `points_prepared` に `configured_win_points` と `configured_lose_points` を保存し、接続世代が対応する接続・切断履歴と結果報告が揃った場合に限り、結果の自分側と相手側の集計値を比較して勝者または敗者の値を選ぶ。設定追加前の履歴は敗者0として扱い、過去の対戦へ新しい敗者配点を遡及加算しない。

「上書きなし」の対戦も無効な付与設定として履歴に記録する。00B4と00B5は送らず、以前の有効な設定を今回の結果へ流用しない。履歴では「サーバー付与なし」と区別する。

累積は電話番号・ユーザー枠0〜3・ゲームID別に既存の台帳へ保存する。結果の再送や同じ対戦について内容を変えた報告で二重加算しない。更新後の累積はコマンド25で端末へ配信し、結果をアップロードした次の対戦・メールサービス応答でも返す。結果をまだ報告していない端末の分を、相手からの報告だけで加算する処理はない。対戦直後のオフライン画面で敗者分が加算されることやROMへの保存完了は保証しない。

履歴の設定ポイントには当該結果で選んだ値、加算額には今回の加算、更新後ポイントにはサーバー累積を表示する。行の詳細には対戦開始時の勝者・敗者双方の設定値を残す。設定や台帳の保存形式はschema 1を維持し、既存の累積・受信済み結果・消費済み対戦の情報を消去しない。

保存済みのPuzzle Bobble 3の勝者・敗者要求を再生し、別の電話番号の勝者へ10、敗者へ3を加算して両端末への25応答と再読み込み後の累積を確認した。8ゲームID×4ユーザーの派生入力では、敗者配点が勝者より大きい場合、0と999、対戦準備後の設定変更、引き分け、未対応の接続履歴、結果の再送を検証した。これらは隔離テストの配点であり、稼働中の値や歴史的な配点ではない。ネイティブ設定・履歴画面は非表示のテスト用画面で確認した。新しい敗者加算が実際のゲーム画面へ反映されることは、次の操作試験で確認する。

## 対戦エリアの確認範囲と残りの検証

隔離テストでは、固定の同一局番内、固定の全国、操作可能な二択の候補について、元のコマンドデコーダーと4C受信処理を実行した。設定ヘッダーと文字列が一致することを確認した。

## ユーザー切り替え後の結果照合（v51、ローカルサーバー方針）

## 対戦結果DB（v55、ローカル追加実装）

旧DataBase_GameResults.cのDataBase_AddGameResultは空実装。DataBase_UpdateRankingは累積勝敗・得失点・xpointsを更新し、DataBase_Core.cにはRankingInfoの保存と復元がある。全対戦の詳細記録は今回の追加実装であり、旧本番サーバーの復元と主張しない。

今回のDBはgame-result-db内の連番JSONファイルによる追記専用のローカル永続ストア（SQLデータベースではない）。新しいサーバーで受け取った構造検証済みコマンド20の84バイトを全て保存する。結果ゲームID、エラー値、自端末/相手の各2プレイヤー結果値、報告時選択ユーザー、既存照合による対戦ユーザー、参加者、対戦接続履歴ID、ポイント算出監査、実際の台帳加算・累積を関連付ける。未照合の所有者と未受信の相手報告は不明。両端末の報告は別行であり、相互一致を確認した単一の確定対戦レコードではない。直近回線の観測IDも別に保存し、それだけで結果の帰属を断定しない。

既存の正常結果抽出・ポイント計算の条件は変更しない。DBのみエラー値が非ゼロの結果も保存し、その結果から加算はしない。結果内の未知バイトは生データのまま保持する。旧GameResultのplayTimeフィールドをサターンの未検証オフセットに当てはめず、対戦時間と単位はnull（不明）。得点比較による勝敗欄は端末報告上の比較であり、ゲーム固有の勝敗規則を解明した意味ではない。

同一電話・生データSHA256・直近観測回線・照合回線・監査/台帳履歴IDが同じ報告は再保存しない。後から照合や台帳情報が追加された場合は新しい版として追記し、元の未照合行は残す。これは一意なROM試合IDが未解明の状況でのローカル重複抑止方針。既存ポイント台帳の消費記録には影響しない。

ファイルは.pendingへ書き込み、FlushFileBuffers後にMOVEFILE_WRITE_THROUGHで確定する。再起動時は連番、スキーマ、生データ長とSHA256を検証。不完全な.pendingや破損があれば起動を止め、勝手に削除・修復しない。保存失敗はGAME_RESULT_DATABASE_ERRORとして報告し、DB画面の保存エラー欄にも表示する。通信バイトは書き換えない。

管理画面は「アクセス・対戦・ポイント履歴」→「対戦結果DB」。一覧は最新順・50件ページ・1秒更新。選択行の下部には生データを含むJSON詳細を表示する。旧履歴やジャーナルの自動移行・過去試合の推定追加はしない。次回起動から収集開始し、再起動ランチャーは既存DBをコピーして保持する。元プロフィールや稼働中サーバーは変更しない。
