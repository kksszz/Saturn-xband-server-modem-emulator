# Saturn XBAND サーバーとモデムの仕様書

対象リリース v0.1.0　実装スナップショット v55　仕様書 第1版　2026年10月7日

本書は、セガサターン版XBANDをローカルで再現するサーバーとモデム部品の実装仕様を説明する。サーバー管理者には設定と保存データ、開発者には通信の層、コマンド、フィールド順序、状態遷移を示す。当時の日本の本番サーバーを完全に復元した仕様ではない。

対象ソースは kksszz/Saturn-xband-server-modem-emulator のタグ v0.1.0、コミット e072d4f。Ymir本体、ROM、BIOS、実際のユーザーデータは配布対象に含まれない。モデム部品を統合したクライアントは別途必要であり、通常版エミュレーターから直接接続できるという意味ではない。

読み方

- 運用と全体構成は1から3、モデムの移植は4と5、サーバーの再実装は6から12を参照する。
- 13に保存先と管理画面、14に試験範囲と未解明事項、15にソースの参照先をまとめる。
- 各項目の根拠を「ROM確認」「旧ソース」「現行実装」「未解明」で区別する。ROM確認には、隔離実行での確認とユーザーの実画面確認があり、両者を同一視しない。

表記規則

- コマンド番号、ROMアドレス、リソース番号、0x付き数値、バイト列は16進数。その他の件数、長さ、時刻は10進数。
- u8、u16、u32は符号なしの1、2、4バイト整数。BEは上位バイトから送るビッグエンディアン。NULは00の1バイト。
- strzはEUC-JP文字列と末尾NUL。長さにNULを含めるかは各形式で明記する。UTF-8の管理用JSONをそのままROMへ送らない。
- opaqueは意味を確定していないフィールド。推測した名前や単位を付けず、必要な生データを保存する。

## 1 対象と確認根拠

現行サーバーはWindows x64用の単一プロセスで、2端末をローカルTCPで接続する。端末ごとに4ユーザー枠を扱う。ゲームごとに独立サーバーを作る構成ではなく、共通XBAND処理にゲームIDを渡す。8ゲームと4枠の派生要求による部品試験は、全タイトルの実プレイ保証ではない。

| 区分 | 意味 | 例 |
| --- | --- | --- |
| ROM確認 | 対象ROMの命令や資源を確認した内容 | 4Cの操作可否、0Eの期限、メールの住所と名前の順序 |
| 旧ソース | 公開SegaServerやSegaOSに実装または定義がある内容 | 待機キュー、配信メール優先、ランク表示の組み立て |
| 現行実装 | 今回の互換処理または運用拡張 | 30ランク編集、勝者と敗者の配点、JSON結果DB |
| 未解明 | 根拠が不足し、確定仕様として採用しない内容 | ROM結果の時間フィールド、当時の時間外拒否応答 |

ROMアドレスの基準は、740960バイトのXBAND.BINを0x06006000へロードした場合である。対象バイナリーのSHA-256は次の値。別バージョンへ同じアドレスを適用しない。

`49ec092d5d109e84540e556103bde534214aee446b57fd89f42a35d0e1e447f3`

旧公開ソースは16ビットSega向けである。共通機構の参照には使うが、コマンド番号や日本語文字列までサターンと同一とは扱わない。コメントに残る予定、空実装、テスト分岐は、本番で実現した機能の証拠ではない。

## 2 構成と通信の層

3種類の形式を区別する。ROMのコマンドは、ホストTCPのJSONメッセージのtypeではない。また対戦中の生バイトをサーバーへのメールコマンドとして解析しない。

| 層 | 内容 | 実装の責務 |
| --- | --- | --- |
| ROMとモデム | カートリッジのバス、UART、AT、ログイン、PPP内のアプリケーション要求 | ROMの入出力をモデム部品が受ける |
| モデムとホスト | 長さ付きJSON v2、Base64のバイナリ転送、advanceによるゲスト時刻通知 | TCP所有者とServiceEndpointが処理する |
| 対戦回線制御 | JSON本文のopとgeneration、発着信、待機通知、async-v1中継 | PairControlが2端末の役割と世代を管理する |

通常の流れは、ROM → UART → モデム通信部品 → ローカルTCP → サーバーのサービス処理である。サーバーの応答は逆方向へ戻る。対戦開始後のゲームデータは対向端末へ中継し、勝敗を中継バイトから推定しない。

| TCPポート | 既定値 | endpoint | 用途 |
| --- | --- | --- | --- |
| base + 0 | 58240 | pb3-0 | 端末1のサービス |
| base + 1 | 58241 | pb3-1 | 端末2のサービス |
| base + 2 | 58242 | peer-0 | 端末1の対戦ペイロード経路 |
| base + 3 | 58243 | peer-1 | 端末2の対戦ペイロード経路 |
| base + 4 | 58244 | call-0 | 端末1の対戦回線制御 |
| base + 5 | 58245 | call-1 | 端末2の対戦回線制御 |

現行実行ファイルは全6ポートを127.0.0.1へbindする。endpointのpb3という名前は開発由来であり、Puzzle Bobble専用という意味ではない。clock_hzはこのサーバー経路で60を要求する。async-v1と外側のwire v2は別のバージョン名である。

同梱の試験キーは小文字aを64個並べた値であり、本番認証として扱わない。TLS、インターネット公開、実電話網への発信、実課金は提供しない。再利用部品にあるLAN許可オプションは、配布サーバーの公開運用を保証しない。

## 3 起動とデータの保全

Windows配布ZIPを展開し、PowerShellでstart-server.ps1を実行する。ソースビルドの場合はbuild/Release/xband-server.exeを使う。モデムクライアントやゲームは起動しない。

```text
.\start-server.ps1
.\start-server.ps1 -BasePort 58440
```

BasePortの範囲は1024から65530。baseからbase+5までを確保する。同じポートの別サーバーとは同時起動できない。Communication Monitorを閉じるとサーバーが終了する。

スクリプトは既存のプロセス環境のXBAND_*変数を一時的に退避し、配布版の明示設定だけで子プロセスを起動する。終了時には呼び出し元の環境を復元する。過去のテスト用環境変数を暗黙に引き継がない。

runtimeに初回の空データ領域を作る。既存のゲーム用テスト環境からメールや台帳を自動取り込む処理ではない。runtimeの実データはGitとリリースZIPへ含めない。

バックアップでは、停止後にruntime全体と設定ファイルを一緒に保存する。ポイント台帳だけを古い版へ戻し、消費済み付与履歴を現在のまま残すような部分復元は避ける。破損や.pendingの残存を見つけても、独断で削除して正常データとして継続しない。

## 4 モデムのバスとAT

現行のModemRegisterBankはゲームから観測したレジスターの部分実装であり、16550や実フラッシュの全仕様ではない。ゲストのバス値はサターンのBE順で渡す。バス操作の幅は1、2、4バイト。UARTアクセスは1バイトである。

| アドレス | 長さ | 現行動作 |
| --- | --- | --- |
| 0x05885029 | 1 | identify有効時に0x11を返す |
| 0x05895001から0x0589501D | 4バイト間隔 | 8個のUARTレジスター |
| 0x04000000から0x0401FFFF | 131072 | フラッシュデータ領域 |
| 0x04000000 と 0x04000001 | 各1 | 識別モードで0x1Fと0xD5 |

UARTのインデックスは(address >> 2) & 7。未処理のバスアクセスは移植側が元のバスへ一度だけ転送する。

| index | 読み出し | 書き込み |
| --- | --- | --- |
| 0 | LCR bit7ならDLL、それ以外は受信FIFO | DLLまたは送信バイト |
| 1 | DLMまたはIER | DLMまたはIER |
| 2 | FIFO状態と割り込み値 | FCR、bit1受信消去、bit2送信消去 |
| 3 | LCR | LCR |
| 4 | MCR | MCR |
| 5 | 送信状態と受信有無bit0 | 対応なし |
| 6 | 0x30とcarrier bit7 | 対応なし |
| 7 | SCR | SCR |

フラッシュのunlockはoffset 0x5555へAA、0x2AAAへ55、その後0x5555へ90で識別、A0で128バイトの書き込みを許可する。F0で識別を解除する。保存先のファイル操作はレジスター部品ではなく移植側が所有する。UARTリセットではフラッシュを消さない。

AT行はCRで確定し、小文字を大文字へ正規化する。行の上限は128バイト。LFは無視する。以下は認識する観測済みの部分集合である。

| AT文字列 | 分類 |
| --- | --- |
| AT | attention |
| ATH0 | hangup |
| ATZ または ATZ0 | reset |
| ATA | answer |
| ATS91=15S92=15DTと番号 | dial、番号は数字とハイフン |
| AT &D0&Q6&S1E0V1&C1W2L3M1S7=30S8=1 | profile |

allowNormalが有効な場合、profileの末尾のバックスラッシュNまたはバックスラッシュN0も受け付ける。設定値を記録することは、スピーカーや誤り訂正の物理機能を再現した証明ではない。+++のガード時間をAT行パーサーだけで再現したとは主張しない。

## 5 ホストTCPのJSON形式

現行実装のフレームは、u32 BEのJSONバイト長に続くUTF-8 JSONである。長さは1から65536。TCPの分割受信と部分送信を許容するが、不正長、重複JSONキー、未知フィールド、深さ上限8に達する構造は拒否する。

共通envelopeには、v、type、endpoint、session、id、reply_to、bodyの7キーを必須とする。vは整数2。idは正の十進文字列で、各方向の受信順序に一致させる。reply_toは応答先idまたはnull。sessionとcallは小文字16進32文字のtoken。helloとhello_okのenvelopeのsessionは空文字列である。

| type | bodyの必須フィールド | 意味 |
| --- | --- | --- |
| hello | client, clock_hz, auth_key | endpointの接続開始 |
| hello_ok | new_session, max_chunk, rx_window | sessionを発行、4096と65536を通知 |
| open | target, subscriber | targetはlocal-service、自局番号を送る |
| open_ok | call | サービス通話が開いた |
| data | call, offset, bytes, payload_b64 | 1から4096バイト、標準Base64 |
| data_ack | call, next_offset, limit | 受理位置と送信可能な上限 |
| advance | call, tick | ここまでのゲスト時刻で処理 |
| advance_ok | call, tick | 対応する処理完了 |
| close | call, reason | reasonはhangupまたはreset |
| close_ok | call | 通話解放完了 |
| ping と pong | 空オブジェクト | 生存確認、pongは対応するreply_to |
| snapshot | call, subscriber, state, sent_bytes, received_bytes, card | 観測状態であり課金命令ではない |
| error | code, message, scope, call | scopeはconnectionまたはcall |

offset、next_offset、limit、tick、累計バイト数も十進文字列で送る。JSONの数値精度によるuint64の欠落を避けるためである。先頭ゼロ付きの複数桁表記は不可。body.bytesは整数で、Base64を復号した長さと一致させる。

```text
{"v":2,"type":"data","endpoint":"pb3-0",
 "session":"00000000000000000000000000000001","id":"3",
 "reply_to":null,"body":{"call":"00000000000000000000000000000002",
 "offset":"0","bytes":1,"payload_b64":"DQ=="}}
```

上記は説明用のCR一文字の例である。tokenを固定して実運用する例ではない。JSONの前には実際のUTF-8バイト長をBEで付ける。

受信窓は65536バイト。ACKはバッファーへの受理を示すだけで、ROMの消費完了ではない。ゲストがconsumeReceivedした分だけ追加creditを返す。通話ごとにoffsetを0へ戻す。

状態はhello → idle → opening → service → closing → idle。hello、open、advance、closeの応答期限は部品上5秒。サーバーは無通信2秒でpingし、5秒以内の対応pongを求める。旧応答や別sessionの返信は受理しない。EOFや時刻逆行などで破棄し、自動再接続や未確認データの再送はしない。

ATZとATH0はrequestCloseを使う。進行中の転送が終わるのを待ち、旧応答を捨ててcloseし、close_ok前に新しいopenや旧CONNECTをゲストへ返さない。全体リセット、ロードステートによる時刻巻き戻し、無効化、終了は接続をstopする。ゲストのUART読み書きの中でネットワーク待ちを行わない。

## 6 ログインとROMコマンドの入口

ログインは受信バイトに基づく限定互換処理である。CR受信でHELO、ゲストフレームを1進めた後にlogin:、PstrnとLFの完全一致でPassword:を返す。続く表示可能ASCII8バイトとLFを数え、次の7EからPPPへ移る。パスワード内容の正式な照合や旧アカウント認証ではない。

PPPは7E区切り、7DによるエスケープとXOR 20、16ビットFCSを使う。アドレスFF、制御03を要求する。実装する主なprotocolはLCP C021、IPCP 8021、IPv4 0021。圧縮と認証のオプションは拒否する。汎用PPP、任意のIP転送、一般TCPスタックではない。

サービス経路の仮想IPはゲスト10.0.0.2、サーバー10.0.0.1、サービスTCP宛先2005。これはホストの58240とは別の番号である。LocalTCPProbeは固定された限定タプルと要求形式を検証する。

ROMのアプリケーション要求は先頭識別 `1F 74 6A 30 34` と登録0Bから始まる。登録の電話番号長はアプリケーション先頭から10進offset22、文字列は23。長さにNULを含む。後続フィールド位置は電話番号長、受信箱申告件数、カードデータ長で移動する。バイト列中にコマンドらしい値を検索する方式は使わない。

| 方向 | コマンド | 現行で扱う内容 |
| --- | --- | --- |
| ROMからサーバー | 0B | 接続ユーザー、申告端末ID、電話番号、受信件数等の登録 |
| ROMからサーバー | 0Eの直後の値 | 02指名、03自動対戦、04メール専用 |
| ROMからサーバー | 1C | 16バイトの対戦設定申告 |
| ROMからサーバー | 1D | 4ユーザーが混在する共有送信箱 |
| ROMからサーバー | 20 | 84バイトの結果ブロック |
| サーバーからROM | 1C と 0E | 着信待機の準備と期限 |
| サーバーからROM | 1D | 発信先番号と照合データ |
| サーバーからROM | 1E | 受信メール一覧 |
| サーバーからROM | 25 | ユーザー別ゲームのポイントとランク |
| サーバーからROM | 32 と 4C | 表示文字列と対戦エリア設定項目 |
| サーバーからROM | 22 と 02 | 通知の登録とサービス正常終了 |

番号が同じでも方向によって形式と意味が異なる。上表は現行対象の一覧であり、ROM全コマンドの完全な一覧ではない。要求中の15、16、21、23、24、26、1B、29などは構造境界の検証にも使うが、本書は未知の意味を正式名称として付けない。

## 7 マッチングと待機

旧Matching_Enqueueはサーバー上の待機登録を保持し、Matchupは発信役に相手番号と照合情報を返す。センターへのサービス通話の正常終了と、マッチング登録の終了は別である。

現行の未成立要求は、受信方向1C、0E、02を返してROMの着信待機へ移す。ROMに「XBANDとの接続を切りました」と表示されても、サーバーの待機登録が即座に消えた意味ではない。待機時にセンター回線を切る構造は旧ソースと一致する。成立後は発信役が対戦相手へ発信し、着信役がATAで応答する。

```text
センター接続 → 要求登録 → 1Cと0Eと02 → センター通話終了
                                            ↓
                                      ROMの着信待機
                           相手成立 → 発着信 → 対戦回線
                           期限終了 → ROM既存の案内 → 登録解除
```

| 受信コマンド | wire形式 | 現行の意味 |
| --- | --- | --- |
| 1C | 1C と8バイトの照合データ | 着信待機の準備。末尾の設定申告とは別 |
| 0E | 0E と u32 BE | ROM内部カウンターで測る期間 |
| 1D | 1D とu8番号長と番号NULと8バイト照合データ | 発信側の相手番号 |
| 02 | 02 | ROMが02を返しサービスを正常終了 |

共通待ち時間は0のみじかい、1のふつう、2のながい。初期値は1分、2分、4分。管理画面で各1から60分、みじかい以下ふつう以下ながいの順に設定でき、同じ値も許可する。全番号、全ID、全ゲーム共通である。

現行換算は分数×3600を0Eへ送る。ROMの期限はVBlank由来のカウンターで進むため、実時間やJSTの時刻とは別であり、停止や実行速度の影響を受ける。0Eのフィールド自体を秒と呼ばない。申し込みの最初に設定を固定し、既に待機中の期限を後から変更しない。

指名先が未待機なら対象名を保持して待機する。別ユーザーを自動的に代わりとして選ばない。指名待機へ独自の開始本文は追加しない。期限終了の通知0062はROMが出し、本文は「あなたにふさわしい対戦相手を見つけることができませんでした。度数は引かれていません。もう一度、対戦を申し込んでください。」の既存資源を使う。ユーザーの実画面でも確認された。

待機準備完了と取消は、読み取り専用の共通XOS観測から通知する。ticketとgenerationを照合し、古い取消で次の申し込みを消さない。これは現行のエミュレーター統合用方式であり、当時のモデムに同じJSON制御があったという意味ではない。

## 8 対戦回線の制御JSON

制御ポートでは、wire v2のdataに以下のJSON本文を載せ、advanceでまとめた要求を処理する。内側には別のu32長を追加しない。1要求は4096バイト以内、前の応答を消費してから次の要求を渡す。

| op | 主なフィールド | 動作 |
| --- | --- | --- |
| join | transport, standby_protocol | async-v1またはlockstepを登録。左右で一致させる |
| poll | op | 現在の状態を取得 |
| standby_ready | generation, ticket | 現在の待機が着信可能になった |
| standby_cancel | generation, ticket | ROMの終了または取消 |
| dial | generation, number | 発信役だけが指定の仮想相手番号へ発信 |
| answer | generation | 着信役が着信中の回線へ応答 |
| exchange | generation, sequence, elapsed, bytes, credit | async-v1のバイト中継 |
| step | generation, elapsed, bytes | 旧lockstep用。async-v1では不可 |
| hangup | generation | 回線を閉じる世代へ移行 |
| closed_ack | generation | 両側の解放完了で次世代へ進む |
| finish | generation | その端末の転送終了。ゲーム勝敗の確定ではない |

```text
{"op":"join","transport":"async-v1",
 "standby_protocol":"xband-readonly-v1"}
{"op":"standby_ready","generation":1,"ticket":1}
{"op":"exchange","generation":1,"sequence":0,
 "elapsed":4096,"bytes":[97,98],"credit":256}
```

数値は内側の制御JSONでは整数。例のsequenceなどは説明用であり、実際の期待順序、carrier状態、creditに従う。外側wireの十進文字列と混同しない。

応答の主なキーはstate、generation、transport、closed、recoverable、caller、callee、joined、finished、grant_end、bytes。待機対応時はstandby内にprotocol、ticket、state、gameも返す。pairのstateは0 idle、1 ringing、2 connected。sideは0と1、callerの2は未割当を表す。

仮想の相手番号はside0から3336666665、side1から3336666666。登録ユーザーの実電話番号そのものではない。番号と発信役の整合性を検査する。

古いgenerationの制御は新しい対戦を変更せず状態照会へ落とす。未来世代は拒否する。closing中はclosed_ack以外で新規操作しない。回線切断を勝敗確定に使わず、結果20を別に扱う。

## 9 対戦エリアと利用時間

4CはROMの設定項目0200:0022を更新し、32は表示用文字列012Eの指定IDを更新する。操作可否と保存された選択値は別の情報である。

| コマンド | 順番に送るフィールド |
| --- | --- |
| 4C | opcode u8、本文長 u32 BE、操作可否 u16 BE、文字列領域 |
| 32 | opcode u8、文字列ID u16 BE、NUL込み文字列長 u32 BE、strz |

4C本文長は操作可否2バイトと文字列領域の合計。操作不可は0000、操作可能は0001。文字列領域は項目名strz、その後に選択肢名strzと説明strzの組を並べる。操作可否を1にするだけでは選択肢は増えない。

任意選択の順序は、対戦エリア:、同一局番内、市外へのコールはしません、全国、長距離通話になる可能性があります。各文字列にNULを付ける。この順序は現行互換設定であり、当時の配信順序の捕捉記録ではない。

| selection | 管理設定 | 4C |
| --- | --- | --- |
| -1 | 上書きしない | 省略、保存済み設定は残る |
| 0 | 同一局番内固定 | 操作不可の一択 |
| 1 | 全国固定 | 操作不可の一択 |
| 2 | ROMで任意選択 | 操作可能の二択 |

32の0052は使用状況の対戦エリア、0054と0055はプレー時間の上段と下段。二行から一行へ戻す場合、0055を空文字へ明示更新する。例は `32 00 55 00 00 00 01 00`。単に送らなくても以前の文字列は消えない。

ROM送信1Cはopcode、長さ10 hex、16バイト本文。次のoffsetはopcodeから数えた16進値である。

| offset | 幅 | 内容 |
| --- | --- | --- |
| 02 | 4 | 変数0049、4ユーザー分のエリア用バイト |
| 06 と 0A | 各4 | 変数0069と006A、意味未確定 |
| 0E | 1 | 選択ユーザーの待ち時間0から2 |
| 0F | 1 | 選択ユーザーのエリア用バイト |
| 10 | 1 | 002D000Fの戻り値、意味未確定 |
| 11 | 1 | 002D0013の戻り値、指名受付とは別 |

指名受付は0Bから数えたoffset09のu32 BE flags bit0。0が「はい」、1が「いいえ」。現行はaccepts_challengesとして観測記録するが、相手判定への適用と当時の拒否応答は未実装である。エリア選択も表示同期までであり、局番による候補の除外は未実装。

曜日別の利用制限は今回のサーバー拡張。電話番号ごとに平日と土日の終日可、指定時間帯、利用不可を設定する。JST、開始を含み終了を含まない。翌日をまたぐ時間帯は前日の許可区間を翌日まで継続する。成立した対戦を強制切断しない。結果報告は受け付ける。

時間外は22と02で正常終了する。現在の本文は「現在は利用時間外です。使用状況をご確認ください。」等の管理用説明であり、当時の時間外本文を復元したものではない。ROMの使用状況表示は32の文字列を表示するだけで、表示の書き換えと制限判定を分ける。

## 10 通知とサービス終了

| コマンド | wire形式 | 確認した意味 |
| --- | --- | --- |
| 22 | opcode、u16 BEを4個、本文長u32 BE、strz | 通知レコード0124を登録 |
| 02 | opcodeのみ | 正常終了、ROMから02返信 |
| 0D | opcode、受信番号u16 BE | 受信処理の登録先を解除 |
| 05 | opcode、マスクu32 BE | 現行では00000004で送信箱消去 |
| 04 | opcode、日付u32 BE、第2値u32 BE | 保存される日時関連の二値 |

22の4個の値は第1が通知フラグ、第2が旧テンプレートID相当、第3と第4が最小と最大の表示時間。サターンの受信経路では第2値を読み捨てる。現行は第2値0000を維持する。

時間外の現行例は `22 00 01 00 00 00 78 01 2C [本文長u32 BE] [strz] 02`。表示時間の値を実時間の秒と断定しない。表示には選択ユーザーや通常メニューの通知マスク等の条件もあり、22を受理しただけで画面表示完了とは扱わない。

02受信の終了値FED3を上位処理が正常終了へ変換する。一般読取失敗のFED2とは区別する。サーバーが意図的な通信エラーを起こして待機終了本文を表示させる設計ではない。

0Dは時間帯設定ではない。解除後に同じ受信番号を処理する全体挙動や、当時の用途は未確定なので、時間外拒否用に送らない。

05による共有送信箱消去は、サーバーが要求全体を保存した後に準備する。全4枠の送信箱に作用するため、一部だけ保存して送らない。ROMの配送完了や受信側の既読ACKではない。

メール日付の現行符号化は `年 << 16 | (月 - 1) << 12 | 日 << 7`。JSTで登録日を算出し、低位7ビットは0とする。その意味や第2値の一般的な単位は未確定。実験用04の固定日付と、配信メールの登録日を混同しない。

## 11 ユーザーとメール形式

1端末に0から3の4枠があり、受信箱は選択ユーザーごとに8件。共有送信箱には別枠の送信メールが混在する。1枠の選択名を他枠の送信者へ流用しない。接続した1枠だけに受信メールを返し、残り3枠は各自の接続時に配送する。

メールのアカウントキーは0Bプロフィールの申告8バイト端末IDと枠。全0または全FFの未登録IDは正規化電話番号と枠へフォールバックする。これは利用者認証や正式なID割り当てを再現する機能ではない。

配送件数はmax(0, 8 - 申告受信件数)。配信メールを通常メールより先に入れ、余ったメールはサーバーに残す。サーバー保管総数に固定件数上限を設ける方針ではないが、ディスクやプロセス資源まで無限とは保証しない。

受信コマンド1Eはopcodeと件数u16 BE、その後に以下のレコードを件数分並べる。

| 順序 | フィールド | wireの幅 |
| --- | --- | --- |
| 1 | allocationBasis | u16 BE |
| 2 | opaqueHeader | 8バイト |
| 3 | opaqueAとopaqueB | 各u8 |
| 4 | opaqueC、アイコンID | u16 BE |
| 5 | field1、住所 | u8長とstrz |
| 6 | field2、差出人名 | u8長とstrz |
| 7 | opaqueD | u16 BE |
| 8 | opaqueE、日付 | u32 BE |
| 9 | field3、件名 | u8長とstrz |
| 10 | field4、本文オブジェクト | u16 BE長とバイナリー |
| 11 | 付加データ長 | u32 BE、現行は0 |

住所を先に、名前を後に送る。ROMのメール本体+0x10が住所、+0x32が名前。v52の逆順はv53で訂正し、実画面で確認した。既にROMに保存された誤順序メールは自動修復しない。

文字列の長さはNUL込み。住所と差出人は各0x22バイト、件名は0x23バイト以内の非重複制約を検査する。これは安全な符号化上限であり、歴史的な最大入力文字数を断定する値ではない。allocationBasis + 4が0x80以上0x7FFF以下、本文が確保領域に収まることも検査する。

応答に格納したメールはprepared_unconfirmedとして提示済み扱いにし、自動再送しない。ROMの受信、既読、永続保存を確認した状態ではない。ROMが同じ送信メールを再提出した場合は別投稿になる。アプリケーション側の再送判断をサーバー独自の配送ACKで置き換えない。

## 12 センター配信とポイント

センター配信は管理者が件名と本文、対象を登録し、対象ユーザーの次回接続で配送する。差出人はXBAND、住所は東京。全ユーザーは将来初めて接続するユーザーも含む。電話番号の全4枠または1枠への指定は現行の拡張である。

アイコンID201、ROMリソース0115:00C9を参照する。32×56、4bppのROM内画像であり、旧ソース画像やROM画像をリリースに同梱しない。センターのopaqueBは0。動画の青い背景の原因は特定済みとは扱わない。

配信本文の非圧縮オブジェクトは次の形式。

```text
flags u16 BE = 0
EUC-JP本文長とNULの合計 u16 BE
checksum u16 BE = 0
本文とNUL
割当パディング u8 = 0
```

全体は本文バイト数+8。allocationBasisは0x80+全体長-4、opaqueDは0x80+全体長。件名32、本文240 EUC-JPバイト以内。日本語は通常2バイト。改行はLFへ正規化し、NUL、絵文字、非標準JISや不要な制御文字を拒否する。通常ユーザーメールの128バイト本文オブジェクト制限とは別。

サンプルメール作成ボタンは歴史的な文面を編集欄へ入れるだけ。配信先を変更せず、自動登録もしない。日付は現在の登録日であり1998年へ偽装しない。

ポイント台帳は電話番号、ユーザー枠、ゲームID別。メールのID識別とは異なる。開始値は0で、固定テスト値100を継続配信しない。勝者と敗者の配点はゲーム別に0から999、勝者-1は両方のサーバー加算なし、引き分け0。対戦開始時に設定を固定し、後からの設定を過去の結果へ適用しない。

32の00B4と00B5は自分と相手の勝利時の価値表示であり、勝者と敗者の付与先ではない。両方へ勝者の値を送り、敗者加算はサーバーの結果照合と累積25で反映する。

25は `25 [resourceID u16 BE] [本文長u16 BE] [本文] [00 00 00 00]`。本文はゲームID u32 BE、ユーザー枠u8、00 u8、ゲーム名strz、現在ランクstrz、累積ポイントstrz、次ランクstrz、必要ポイントstrz。resourceIDは枠×64+ゲームslot。現行の台帳経路は4枠分を返す。

ランクは30段階、初期閾値0、200、400から5800まで。閾値は厳密な昇順で最初0、最大999999999。単位はLEVEL、段、級からゲーム別に設定し、昇順または逆順の表示を選ぶ。30ランクと一律200幅は現行の設定可能な初期方針であり、全ゲームの当時の条件を解明した結果ではない。

## 13 対戦結果と保存先

ROM送信20の84バイトは端末共通リソース012A:0からの結果である。現在選択しているユーザーが結果の所有者とは限らない。次のoffsetはopcodeを除き、サイズワードを先頭とした10進値である。

| offset | 幅 | 確認したフィールド |
| --- | --- | --- |
| 0 | 4 | ブロック長84、u32 BE |
| 4 | 4 | ゲームID |
| 8 | 4 | game_error |
| 12 と16 | 各4 | 自端末側の2プレイヤー結果値 |
| 20 と24 | 各4 | 相手側の2プレイヤー結果値 |
| 28から83 | 56 | 未確定部分、生データ保存 |

現行は直近の実際の対戦回線の参加者と開始時の配点、切断を照合して付与先を選ぶ。22で対戦して21からメール接続しても、報告者21と参加者22を別に記録し、照合できた22へ加算する。実画面での確認あり。複数の古い未送信結果の一意な帰属は保証しない。

正常結果だけを既存ポイント計算へ使う。自端末2値の合計と相手2値の合計を比較して配点を選ぶが、この比較を各ゲーム固有の勝敗ルールの解明とは呼ばない。相手からの報告だけで未報告端末へ加算しない。

結果DBはSQLではなく追記専用JSON。生データ84バイト、SHA256、報告ユーザー、照合ユーザー、参加者、対戦接続ID、監査と台帳受領記録を関連付ける。game_errorが非0でもDBには残すが、そこからポイントを加算しない。play_timeとunitはnullのまま。旧ソースの同名フィールドを推測位置へ当てはめない。

同一電話番号、生データhash、直近観測回線、照合回線、監査ID、台帳IDが一致する報告は再保存しない。後で照合情報が追加されたら新しい版を追記する。両端末の報告は別行で、相互一致した単一確定試合DBではない。旧試合を推測して遡及登録しない。

| runtime内の名前 | 内容 | 指定環境変数 |
| --- | --- | --- |
| mail-journal | 通常メール、.broadcast、.offers | XBAND_LOCAL_MAIL_JOURNAL_DIR |
| activity-history | アクセス、待機、発着信、付与監査 | XBAND_ACTIVITY_HISTORY_DIR |
| game-result-db | 連番の結果JSON | XBAND_GAME_RESULT_DB_DIR |
| game-point-ledger.json | 累積と重複加算抑止 | XBAND_GAME_POINT_LEDGER_FILE |
| game-ranking-settings.json | 表示字段、勝者と敗者の配点 | XBAND_GAME_RANKING_FILE |
| game-level-settings.json | 30閾値と表示単位 | XBAND_GAME_LEVEL_FILE |
| usage-area-settings.json | エリア、時間表示、曜日ルール | XBAND_USAGE_AREA_FILE |
| standby-wait-settings.json | 共通の3待ち時間 | XBAND_STANDBY_WAIT_FILE |

結果DBは.pendingへ書き、FlushFileBuffers後にMOVEFILE_WRITE_THROUGHで確定する。再読込で連番、スキーマ、長さ、hashを検証し、不完全データでは停止する。保存失敗はGAME_RESULT_DATABASE_ERRORとしてログと画面に示し、ROMの通信バイトを都合よく書き換えない。

管理画面にはメール履歴、センター配信、アクセスと対戦とポイントの履歴、対戦結果DBを分けて置く。結果DBは最新順50件、1秒更新、JSON詳細付き。中継1→2と2→1の文字列表示はASCII可視文字を表示し、その他を\\xHHで示す。日本語本文やゲームデータの意味を自動復号した表示ではない。

## 14 検証範囲と未解明事項

リリースの独立ビルドと45件のCTestを実施済み。部品試験では8ゲーム×4枠、待ち時間、容量、切り替え、再報告、再起動などの派生ケースを扱う。ROM隔離実行はストリーム、DB、時計、画面のバックエンド等を代替するため、実機試験と区別する。

| 項目 | 現時点の範囲 |
| --- | --- |
| 4Cと32 | エリア任意選択と使用時間の実画面確認あり |
| 0E | 期限比較のROM実行と既存終了本文の実画面確認あり |
| メール | 対戦経由受信、XBANDアイコン、住所と名前、サンプル全文を実画面確認 |
| ユーザー切り替え | 22の対戦後21接続で22へ累積反映する試験と実画面確認 |
| 配点とランク | 台帳と設定の部品試験。全ゲームの勝者と敗者の実操作確認ではない |

未解明または未実装の主要項目は、当時の日本サーバーの認証と課金、指名受付拒否の正常応答、地域による対戦候補の絞り込み、歴史的なゲーム別配点とランク条件、ROM自身の時間帯判定、結果IDと古い複数結果の所有者、結果内の時間の位置と単位である。

旧DataBase_AddGameResultは公開版では空実装。UpdateRankingとRankingInfoの保存はあるが、今回の全報告DBをそのまま当時の完成機能とは呼ばない。旧UpdateRankingの仮対応ゲームや引き分け処理も現行仕様へ無条件に流用しない。

ROM内の0120-717360はセンター発信先として確認した番号。東京専用番号との証明ではない。青い背景と緑の背景の差は未解明で、サーバーのテーマ制御として実装しない。UARTの全物理特性、ビット波形、全割り込み、全ゲームの実行互換性も完成保証の対象外である。
