# Saturn XBAND サーバーとモデムの仕様書

対象リリース v0.2.0　v55以降の共通度数対応　仕様書 第2版　2026年10月9日

本書は、セガサターン版XBANDをローカルで再現するサーバーとモデム部品の実装仕様を説明する。サーバー管理者には設定と保存データ、開発者には通信の層、コマンド、フィールド順序、状態遷移を示す。当時の日本の本番サーバーを完全に復元した仕様ではない。

SH-2内蔵SCIを使う対戦ケーブルの独立した通信経路は、別冊の[対戦ケーブルのシリアル通信エミュレート仕様](BATTLE-CABLE-SERIAL-SPEC.md)を参照する。XBANDモデムのUARTやサーバーの対戦中継とは別の機構である。

対象は kksszz/Saturn-xband-server-modem-emulator のv0.2.0向けソースである。初回タグv0.1.0、コミットe072d4fの仕様を基に、有限カード、全タイトル共通料金、端末別精算、ゲーム標準定義、表示修正を統合した。v0.2.0へ収録する追加であり、既存v0.1.0の実行ファイル・ZIP・PDFを上書きしたという意味ではない。Ymir本体、ゲームDISC(ROM)、BIOS、実際のユーザーデータは配布対象に含まれない。モデム部品を統合したクライアントは別途必要であり、通常版エミュレーターから直接接続できるという意味ではない。

読み方

- 運用と全体構成は1から3、モデムの移植は4と5を参照する。
- 6がゲームDISC(ROM)通信コマンド一覧、5がモデム接続用JSON一覧、8が対戦回線用JSON一覧。コマンド番号とJSONのtype／opを混同しない。
- 7から12に待機・使用状況・メール・ポイント、13に結果と保存先、14に検証範囲、15に度数とカード、16に実装の参照先と標準ゲーム定義をまとめる。
- 各項目の根拠を「ゲームDISC(ROM)確認」「旧ソース」「現行実装」「未解明」で区別する。ゲームDISC(ROM)確認には、隔離実行での確認とユーザーの実画面確認があり、両者を同一視しない。

現在の共通方針

- 度数処理と料金設定は全タイトル共通。メール標準1、通常対戦標準3、途中リセットの対戦分は両側各1固定。精算時のメール料金は別に加算する。
- 正常対戦・リセット後は、各端末自身の新しい結果を次回接続で照合して個別に精算する。相手の再接続を待たない。
- ゲーム別に変更するのは勝者・敗者ポイントとランク条件。ゲームIDは表示・マッチング・結果の帰属に使い、料金の分岐に使わない。
- カード実績・残数差・識別を確認して精算台帳を確定する。結果不明の再請求、自動補充、返還は行わない。

表記規則

- コマンド番号、ゲームDISC(ROM)アドレス、リソース番号、0x付き数値、バイト列は16進数。その他の件数、長さ、時刻は10進数。
- u8、u16、u32は符号なしの1、2、4バイト整数。BEは上位バイトから送るビッグエンディアン。NULは00の1バイト。
- strzはEUC-JP文字列と末尾NUL。長さにNULを含めるかは各形式で明記する。UTF-8の管理用JSONをそのままゲームDISC(ROM)へ送らない。
- opaqueは意味を確定していないフィールド。推測した名前や単位を付けず、必要な生データを保存する。

## 1 対象と確認根拠

現行サーバーはWindows x64用の単一プロセスで、2端末をローカルTCPで接続する。端末ごとに4ユーザー枠を扱う。ゲームごとに独立サーバーを作る構成ではなく、共通XBAND処理にゲームIDを渡す。8ゲームと4枠の派生要求による部品試験は、全タイトルの実プレイ保証ではない。

| 区分 | 意味 | 例 |
| --- | --- | --- |
| ゲームDISC(ROM)確認 | 対象ゲームDISC(ROM)の命令や資源を確認した内容 | 4Cの操作可否、0Eの期限、メールの住所と名前の順序 |
| 旧ソース | 公開SegaServerやSegaOSに実装または定義がある内容 | 待機キュー、配信メール優先、ランク表示の組み立て |
| 現行実装 | 今回の互換処理または運用拡張 | 30ランク編集、勝者と敗者の配点、JSON結果DB |
| 未解明 | 根拠が不足し、確定仕様として採用しない内容 | ゲームDISC(ROM)結果の時間フィールド、当時の時間外拒否応答 |

ゲームDISC(ROM)アドレスの基準は、740960バイトのXBAND.BINを0x06006000へロードした場合である。対象バイナリーのSHA-256は次の値。別バージョンへ同じアドレスを適用しない。

`49ec092d5d109e84540e556103bde534214aee446b57fd89f42a35d0e1e447f3`

旧公開ソースは16ビットSega向けである。共通機構の参照には使うが、コマンド番号や日本語文字列までサターンと同一とは扱わない。コメントに残る予定、空実装、テスト分岐は、本番で実現した機能の証拠ではない。

## 2 構成と通信の層

3種類の形式を区別する。ゲームDISC(ROM)のコマンドは、ホストTCPのJSONメッセージのtypeではない。また対戦中の生バイトをサーバーへのメールコマンドとして解析しない。

| 層 | 内容 | 実装の責務 |
| --- | --- | --- |
| ゲームDISC(ROM)とモデム | カートリッジのバス、UART、AT、ログイン、PPP内のアプリケーション要求 | ゲームDISC(ROM)の入出力をモデム部品が受ける |
| モデムとホスト | 長さ付きJSON v2、Base64のバイナリ転送、advanceによるゲスト時刻通知 | TCP所有者とServiceEndpointが処理する |
| 対戦回線制御 | JSON本文のopとgeneration、発着信、待機通知、async-v1中継 | PairControlが2端末の役割と世代を管理する |

通常の流れは、ゲームDISC(ROM) → UART → モデム通信部品 → ローカルTCP → サーバーのサービス処理である。サーバーの応答は逆方向へ戻る。対戦開始後のゲームデータは対向端末へ中継し、勝敗を中継バイトから推定しない。

| TCPポート | 既定値 | endpoint | 用途 |
| --- | --- | --- | --- |
| base + 0 | 58240 | pb3-0 | 端末1のサービス |
| base + 1 | 58241 | pb3-1 | 端末2のサービス |
| base + 2 | 58242 | peer-0 | 端末1の対戦ペイロード経路 |
| base + 3 | 58243 | peer-1 | 端末2の対戦ペイロード経路 |
| base + 4 | 58244 | call-0 | 端末1の対戦回線制御 |
| base + 5 | 58245 | call-1 | 端末2の対戦回線制御 |

現行実行ファイルは全6ポートを127.0.0.1へbindする。endpointのpb3という名前は開発由来であり、Puzzle Bobble専用という意味ではない。clock_hzはこのサーバー経路で60を要求する。async-v1と外側のwire v2は別のバージョン名である。

同梱の試験キーは小文字aを64個並べた値であり、本番認証として扱わない。TLS、インターネット公開、実電話網への発信、実課金は提供しない。再利用部品にあるLAN許可オプションは、配布サーバーの公開運用を保証しない。

## 3 起動とデータの保全

Windows配布ZIPを展開し、PowerShellでstart-server.ps1を実行する。ソースビルドの場合はbuild/Release/xband-server.exeを使う。モデムクライアントやゲームは起動しない。

```text
.\start-server.ps1
.\start-server.ps1 -BasePort 58440
```

BasePortの範囲は1024から65530。baseからbase+5までを確保する。同じポートの別サーバーとは同時起動できない。Communication Monitorを閉じるとサーバーが終了する。

スクリプトは既存のプロセス環境のXBAND_*変数を一時的に退避し、配布版の明示設定だけで子プロセスを起動する。終了時には呼び出し元の環境を復元する。過去のテスト用環境変数を暗黙に引き継がない。

runtimeに初回の空データ領域を作る。既存のゲーム用テスト環境からメールや台帳を自動取り込む処理ではない。runtimeの実データはGitとリリースZIPへ含めない。

バックアップでは、停止後にruntime全体と設定ファイルを一緒に保存する。ポイント台帳だけを古い版へ戻し、消費済み付与履歴を現在のまま残すような部分復元は避ける。破損や.pendingの残存を見つけても、独断で削除して正常データとして継続しない。

## 4 モデムのバスとAT

現行のModemRegisterBankはゲームから観測したレジスターの部分実装であり、16550や実フラッシュの全仕様ではない。ゲストのバス値はサターンのBE順で渡す。バス操作の幅は1、2、4バイト。UARTアクセスは1バイトである。

| アドレス | 長さ | 現行動作 |
| --- | --- | --- |
| 0x05885029 | 1 | identify有効時に0x11を返す |
| 0x05895001から0x0589501D | 4バイト間隔 | 8個のUARTレジスター |
| 0x04000000から0x0401FFFF | 131072 | フラッシュデータ領域 |
| 0x04000000 と 0x04000001 | 各1 | 識別モードで0x1Fと0xD5 |

UARTのインデックスは(address >> 2) & 7。未処理のバスアクセスは移植側が元のバスへ一度だけ転送する。

| index | 読み出し | 書き込み |
| --- | --- | --- |
| 0 | LCR bit7ならDLL、それ以外は受信FIFO | DLLまたは送信バイト |
| 1 | DLMまたはIER | DLMまたはIER |
| 2 | FIFO状態と割り込み値 | FCR、bit1受信消去、bit2送信消去 |
| 3 | LCR | LCR |
| 4 | MCR | MCR |
| 5 | 送信状態と受信有無bit0 | 対応なし |
| 6 | 0x30とcarrier bit7 | 対応なし |
| 7 | SCR | SCR |

フラッシュのunlockはoffset 0x5555へAA、0x2AAAへ55、その後0x5555へ90で識別、A0で128バイトの書き込みを許可する。F0で識別を解除する。保存先のファイル操作はレジスター部品ではなく移植側が所有する。UARTリセットではフラッシュを消さない。

AT行はCRで確定し、小文字を大文字へ正規化する。行の上限は128バイト。LFは無視する。以下は認識する観測済みの部分集合である。

| AT文字列 | 分類 |
| --- | --- |
| AT | attention |
| ATH0 | hangup |
| ATZ または ATZ0 | reset |
| ATA | answer |
| ATS91=15S92=15DTと番号 | dial、番号は数字とハイフン |
| AT &D0&Q6&S1E0V1&C1W2L3M1S7=30S8=1 | profile |

allowNormalが有効な場合、profileの末尾のバックスラッシュNまたはバックスラッシュN0も受け付ける。設定値を記録することは、スピーカーや誤り訂正の物理機能を再現した証明ではない。+++のガード時間をAT行パーサーだけで再現したとは主張しない。

## 5 ホストTCPのJSON形式

現行実装のフレームは、u32 BEのJSONバイト長に続くUTF-8 JSONである。長さは1から65536。TCPの分割受信と部分送信を許容するが、不正長、重複JSONキー、未知フィールド、深さ上限8に達する構造は拒否する。

共通envelopeには、v、type、endpoint、session、id、reply_to、bodyの7キーを必須とする。vは整数2。idは正の十進文字列で、各方向の受信順序に一致させる。reply_toは応答先idまたはnull。sessionとcallは小文字16進32文字のtoken。helloとhello_okのenvelopeのsessionは空文字列である。

| type | bodyの必須フィールド | 意味 |
| --- | --- | --- |
| hello | client, clock_hz, auth_key | endpointの接続開始 |
| hello_ok | new_session, max_chunk, rx_window | sessionを発行、4096と65536を通知 |
| open | target, subscriber | targetはlocal-service、自局番号を送る |
| open_ok | call | サービス通話が開いた |
| data | call, offset, bytes, payload_b64 | 1から4096バイト、標準Base64 |
| data_ack | call, next_offset, limit | 受理位置と送信可能な上限 |
| advance | call, tick | ここまでのゲスト時刻で処理 |
| advance_ok | call, tick | 対応する処理完了 |
| close | call, reason | reasonはhangupまたはreset |
| close_ok | call | 通話解放完了 |
| ping と pong | 空オブジェクト | 生存確認、pongは対応するreply_to |
| snapshot | call, subscriber, state, sent_bytes, received_bytes, card | 観測状態であり課金命令ではない |
| error | code, message, scope, call | scopeはconnectionまたはcall |

offset、next_offset、limit、tick、累計バイト数も十進文字列で送る。JSONの数値精度によるuint64の欠落を避けるためである。先頭ゼロ付きの複数桁表記は不可。body.bytesは整数で、Base64を復号した長さと一致させる。

```text
{"v":2,"type":"data","endpoint":"pb3-0",
 "session":"00000000000000000000000000000001","id":"3",
 "reply_to":null,"body":{"call":"00000000000000000000000000000002",
 "offset":"0","bytes":1,"payload_b64":"DQ=="}}
```

上記は説明用のCR一文字の例である。tokenを固定して実運用する例ではない。JSONの前には実際のUTF-8バイト長をBEで付ける。

受信窓は65536バイト。ACKはバッファーへの受理を示すだけで、ゲームDISC(ROM)の消費完了ではない。ゲストがconsumeReceivedした分だけ追加creditを返す。通話ごとにoffsetを0へ戻す。

状態はhello → idle → opening → service → closing → idle。hello、open、advance、closeの応答期限は部品上5秒。サーバーは無通信2秒でpingし、5秒以内の対応pongを求める。旧応答や別sessionの返信は受理しない。EOFや時刻逆行などで破棄し、自動再接続や未確認データの再送はしない。

ATZとATH0はrequestCloseを使う。進行中の転送が終わるのを待ち、旧応答を捨ててcloseし、close_ok前に新しいopenや旧CONNECTをゲストへ返さない。全体リセット、ロードステートによる時刻巻き戻し、無効化、終了は接続をstopする。ゲストのUART読み書きの中でネットワーク待ちを行わない。

## 6 ゲームDISC(ROM)通信の入口とコマンド一覧

ログインは受信バイトに基づく限定互換処理である。CR受信でHELO、ゲストフレームを1進めた後にlogin:、PstrnとLFの完全一致でPassword:を返す。続く表示可能ASCII8バイトとLFを数え、次の7EからPPPへ移る。パスワード内容の正式な照合や旧アカウント認証ではない。

PPPは7E区切り、7DによるエスケープとXOR 20、16ビットFCSを使う。アドレスFF、制御03を要求する。実装する主なprotocolはLCP C021、IPCP 8021、IPv4 0021。圧縮と認証のオプションは拒否する。汎用PPP、任意のIP転送、一般TCPスタックではない。

サービス経路の仮想IPはゲスト10.0.0.2、サーバー10.0.0.1、サービスTCP宛先2005。これはホストの58240とは別の番号である。LocalTCPProbeは固定された限定タプルと要求形式を検証する。

ゲームDISC(ROM)のアプリケーション要求は先頭識別 `1F 74 6A 30 34` と登録0Bから始まる。登録の電話番号長はアプリケーション先頭から10進offset22、文字列は23。長さにNULを含む。後続フィールド位置は電話番号長、受信箱申告件数、カードデータ長で移動する。バイト列中にコマンドらしい値を検索する方式は使わない。

### 6.1 サーバーからゲームDISC(ROM)へのコマンド

以下は現在使用する応答と、用途を限定した確認済み応答の一覧。番号は16進数。ゲームDISC(ROM)が持つ全命令の一覧ではなく、管理者が任意の番号を直接送るコンソールAPIでもない。

| 番号 | 用途 | 本文の概略 | 適用と確認範囲 |
| --- | --- | --- | --- |
| 02 | サービス正常終了 | 本文なし | ゲームDISC(ROM)から02が返る。対戦の勝敗確定ではない |
| 04 | 日時関連値の更新 | u32 BEを2個 | 保存経路確認。第2値の一般的な単位は未確定、固定日付配信は試験設定 |
| 05 | 保存済み要求の送信箱消去 | マスクu32 BE | 00000004で全4枠の共有送信箱を消去。全体保存後に準備し、受信側配送ACKとはしない |
| 0D | 受信処理の登録解除 | 受信番号u16 BE | ゲームDISC(ROM)受信処理を確認。時間外拒否や度数不足のためには送らない |
| 0E | 着信待機の期限 | 期間u32 BE | ゲームDISC(ROM)内部カウンター値。共通待ち時間を換算し、実秒値とは区別する |
| 1C | 着信待機の準備 | 照合データ8バイト | 未成立のマッチング要求に0E・02と組み合わせる |
| 1D | 発信役への相手情報 | 番号長u8、番号strz、照合データ8バイト | 発信先は仮想対戦番号。登録電話番号そのものではない |
| 1E | 受信メール一覧 | 件数u16 BE、メールレコード列 | メールの空き容量に応じて格納。提示済みと実受信完了は別 |
| 22 | 通知の登録 | u16 BEを4個、本文長u32 BE、strz | 待機案内・管理用時間外案内・度数不足案内。本文の出典を区別する |
| 25 | ポイントとランク表示 | 資源IDu16 BE、本文長u16 BE、本文、末尾4バイト | 電話番号・ユーザー枠・ゲーム別の累積と設定を反映 |
| 32 | 表示文字列の更新 | 文字列IDu16 BE、長さu32 BE、strz | 0052エリア、0054／0055時間、008Bタイトル、00B4／00B5価値表示など |
| 49 | カード度数の消費要求 | 要求量u32 BE、照合長u32 BE、カード照合データ | 明示有効化された共通料金の精算。完全なゲームDISC(ROM)返信1Eを照合して確定 |
| 4C | 対戦エリア設定項目の更新 | 本文長u32 BE、操作可否u16 BE、文字列領域 | 表示選択肢と操作可否を更新。保存済み選択値とは別 |

32／4Cの詳細は9、22／02／04／05／0Dは10、メール1Eは11、25は12、49は15を参照する。strzの長さは各形式の指定に従い、UTF-8の管理用文字列を直接送らない。

### 6.2 ゲームDISC(ROM)からサーバーへのコマンド

| 番号 | 用途 | 本文の概略 | サーバーの扱い |
| --- | --- | --- | --- |
| 02 | サービス終了応答 | 本文なし | サーバーからの02に対応する終了処理 |
| 0B | 接続登録 | 可変長プロフィール、端末ID、電話番号、ユーザー枠、受信件数等 | 構造を検証する。正式な利用者認証とはしない |
| 0E | サービス種別 | 後続値02＝指名、03＝自動対戦、04＝メール | 指名の場合は対象名の長さと本文も検証。値02等を独立コマンドと混同しない |
| 15／16 | 資源リスト | 件数・長さ付きレコード | 観測済み形式の境界を検証。未知資源の意味を推測しない |
| 1C | 対戦設定申告 | 長さu8＝10 hex、本文16バイト | エリア・待ち時間等の申告。受信方向の着信準備1Cとは別 |
| 1D | 共有送信箱の提出 | 件数u16 BE、各枠の送信レコード | 選択枠以外の投稿も保存し、全体保存後の05と対応させる |
| 1E | 接続時のカード報告 | 00、残数signed BE16、長さu32 BE、カードデータ | 消費実績の末尾がない8／21バイト。申告だけでは課金許可にならない |
| 1E | 49への完全な消費返信 | 上記カード報告＋実消費signed BE32 | 12／25バイト。要求額・カード識別・残数差・台帳を検証する |
| 20 | 通常の結果報告 | サイズワードから84バイトの結果 | 生データを保存し、帰属を照合してポイントと通常対戦精算へ使う |
| 23 | 異常・未完了の結果報告 | サイズワードから84バイトの結果 | 生データを保存。−608／−609のみ共通リセット料金に分類し、他コードは自動で読み替えない |
| 21／24／26／1B／29 | 要求の区切りと後続データ | 観測済み末尾形式 | 構造検証用。意味未確定の値を配送ACKや課金確定として使わない |

1Eは方向だけでなく接続登録・消費返信という文脈でも区別する。49への返信の先頭1Eだけ、または隔離試験用の5バイトの実績断片だけで通常通信の消費完了を判定しない。

### 6.3 解析済みでも通常運用へ採用していないコマンド

解析記録には0C、2C、2D、3A／3B／3C、42／43、47などのゲームDISC(ROM)受信・保存・返信経路も残る。現在の通常サービスの認証・課金・補償命令として任意に送信する仕様は設けない。特にカードの案内資源IDと通信コマンド番号を混同しない。個々の原命令試験と未解明部分は[コマンド解析記録](XBAND-COMMAND-SPEC-DRAFT.md)に分離する。

地域表示用38の試験配信は特定要求に限る既存の診断経路であり、度数の共通化対象や全タイトル共通の通常返信として数えない。料金を38の有無やゲーム名から分岐させない。

## 7 マッチングと待機

旧Matching_Enqueueはサーバー上の待機登録を保持し、Matchupは発信役に相手番号と照合情報を返す。センターへのサービス通話の正常終了と、マッチング登録の終了は別である。

現行の未成立要求は、受信方向1C、0E、02を返してゲームDISC(ROM)の着信待機へ移す。ゲームDISC(ROM)に「XBANDとの接続を切りました」と表示されても、サーバーの待機登録が即座に消えた意味ではない。待機時にセンター回線を切る構造は旧ソースと一致する。成立後は発信役が対戦相手へ発信し、着信役がATAで応答する。

```text
センター接続 → 要求登録 → 1Cと0Eと02 → センター通話終了
                                            ↓
                                      ゲームDISC(ROM)の着信待機
                           相手成立 → 発着信 → 対戦回線
                           期限終了 → ゲームDISC(ROM)既存の案内 → 登録解除
```

| 受信コマンド | wire形式 | 現行の意味 |
| --- | --- | --- |
| 1C | 1C と8バイトの照合データ | 着信待機の準備。末尾の設定申告とは別 |
| 0E | 0E と u32 BE | ゲームDISC(ROM)内部カウンターで測る期間 |
| 1D | 1D とu8番号長と番号NULと8バイト照合データ | 発信側の相手番号 |
| 02 | 02 | ゲームDISC(ROM)が02を返しサービスを正常終了 |

共通待ち時間は0のみじかい、1のふつう、2のながい。初期値は1分、2分、4分。管理画面で各1から60分、みじかい以下ふつう以下ながいの順に設定でき、同じ値も許可する。全番号、全ID、全ゲーム共通である。

現行換算は分数×3600を0Eへ送る。ゲームDISC(ROM)の期限はVBlank由来のカウンターで進むため、実時間やJSTの時刻とは別であり、停止や実行速度の影響を受ける。0Eのフィールド自体を秒と呼ばない。申し込みの最初に設定を固定し、既に待機中の期限を後から変更しない。

指名先が未待機なら対象名を保持して待機する。別ユーザーを自動的に代わりとして選ばない。指名待機へ独自の開始本文は追加しない。期限終了の通知0062はゲームDISC(ROM)が出し、本文は「あなたにふさわしい対戦相手を見つけることができませんでした。度数は引かれていません。もう一度、対戦を申し込んでください。」の既存資源を使う。ユーザーの実画面でも確認された。

待機準備完了と取消は、読み取り専用の共通XOS観測から通知する。ticketとgenerationを照合し、古い取消で次の申し込みを消さない。これは現行のエミュレーター統合用方式であり、当時のモデムに同じJSON制御があったという意味ではない。

## 8 対戦回線の制御JSON

制御ポートでは、wire v2のdataに以下のJSON本文を載せ、advanceでまとめた要求を処理する。内側には別のu32長を追加しない。1要求は4096バイト以内、前の応答を消費してから次の要求を渡す。

| op | 主なフィールド | 動作 |
| --- | --- | --- |
| join | transport, standby_protocol | async-v1またはlockstepを登録。左右で一致させる |
| poll | op | 現在の状態を取得 |
| standby_ready | generation, ticket | 現在の待機が着信可能になった |
| standby_cancel | generation, ticket | ゲームDISC(ROM)の終了または取消 |
| dial | generation, number | 発信役だけが指定の仮想相手番号へ発信 |
| answer | generation | 着信役が着信中の回線へ応答 |
| exchange | generation, sequence, elapsed, bytes, credit | async-v1のバイト中継 |
| step | generation, elapsed, bytes | 旧lockstep用。async-v1では不可 |
| hangup | generation | 回線を閉じる世代へ移行 |
| closed_ack | generation | 両側の解放完了で次世代へ進む |
| finish | generation | その端末の転送終了。ゲーム勝敗の確定ではない |

```text
{"op":"join","transport":"async-v1",
 "standby_protocol":"xband-readonly-v1"}
{"op":"standby_ready","generation":1,"ticket":1}
{"op":"exchange","generation":1,"sequence":0,
 "elapsed":4096,"bytes":[97,98],"credit":256}
```

数値は内側の制御JSONでは整数。例のsequenceなどは説明用であり、実際の期待順序、carrier状態、creditに従う。外側wireの十進文字列と混同しない。

応答の主なキーはstate、generation、transport、closed、recoverable、caller、callee、joined、finished、grant_end、bytes。待機対応時はstandby内にprotocol、ticket、state、gameも返す。pairのstateは0 idle、1 ringing、2 connected。sideは0と1、callerの2は未割当を表す。

仮想の相手番号はside0から3336666665、side1から3336666666。登録ユーザーの実電話番号そのものではない。番号と発信役の整合性を検査する。

古いgenerationの制御は新しい対戦を変更せず状態照会へ落とす。未来世代は拒否する。closing中はclosed_ack以外で新規操作しない。回線切断を勝敗確定に使わず、結果20を別に扱う。

## 9 対戦エリアと利用時間

4CはゲームDISC(ROM)の設定項目0200:0022を更新し、32は表示用文字列012Eの指定IDを更新する。操作可否と保存された選択値は別の情報である。

| コマンド | 順番に送るフィールド |
| --- | --- |
| 4C | opcode u8、本文長 u32 BE、操作可否 u16 BE、文字列領域 |
| 32 | opcode u8、文字列ID u16 BE、NUL込み文字列長 u32 BE、strz |

4C本文長は操作可否2バイトと文字列領域の合計。操作不可は0000、操作可能は0001。文字列領域は項目名strz、その後に選択肢名strzと説明strzの組を並べる。操作可否を1にするだけでは選択肢は増えない。

任意選択の順序は、対戦エリア:、同一局番内、市外へのコールはしません、全国、長距離通話になる可能性があります。各文字列にNULを付ける。この順序は現行互換設定であり、当時の配信順序の捕捉記録ではない。

| selection | 管理設定 | 4C |
| --- | --- | --- |
| -1 | 上書きしない | 省略、保存済み設定は残る |
| 0 | 同一局番内固定 | 操作不可の一択 |
| 1 | 全国固定 | 操作不可の一択 |
| 2 | ゲームDISC(ROM)で任意選択 | 操作可能の二択 |

32の0052は使用状況の対戦エリア、0054と0055はプレー時間の上段と下段。二行から一行へ戻す場合、0055を空文字へ明示更新する。例は `32 00 55 00 00 00 01 00`。単に送らなくても以前の文字列は消えない。

ゲームDISC(ROM)送信1Cはopcode、長さ10 hex、16バイト本文。次のoffsetはopcodeから数えた16進値である。

| offset | 幅 | 内容 |
| --- | --- | --- |
| 02 | 4 | 変数0049、4ユーザー分のエリア用バイト |
| 06 と 0A | 各4 | 変数0069と006A、意味未確定 |
| 0E | 1 | 選択ユーザーの待ち時間0から2 |
| 0F | 1 | 選択ユーザーのエリア用バイト |
| 10 | 1 | 002D000Fの戻り値、意味未確定 |
| 11 | 1 | 002D0013の戻り値、指名受付とは別 |

指名受付は0Bから数えたoffset09のu32 BE flags bit0。0が「はい」、1が「いいえ」。現行はaccepts_challengesとして観測記録するが、相手判定への適用と当時の拒否応答は未実装である。エリア選択も表示同期までであり、局番による候補の除外は未実装。

曜日別の利用制限は今回のサーバー拡張。電話番号ごとに平日と土日の終日可、指定時間帯、利用不可を設定する。JST、開始を含み終了を含まない。翌日をまたぐ時間帯は前日の許可区間を翌日まで継続する。成立した対戦を強制切断しない。結果報告は受け付ける。

時間外は22と02で正常終了する。現在の本文は「現在は利用時間外です。使用状況をご確認ください。」等の管理用説明であり、当時の時間外本文を復元したものではない。ゲームDISC(ROM)の使用状況表示は32の文字列を表示するだけで、表示の書き換えと制限判定を分ける。

## 10 通知とサービス終了

| コマンド | wire形式 | 確認した意味 |
| --- | --- | --- |
| 22 | opcode、u16 BEを4個、本文長u32 BE、strz | 通知レコード0124を登録 |
| 02 | opcodeのみ | 正常終了、ゲームDISC(ROM)から02返信 |
| 0D | opcode、受信番号u16 BE | 受信処理の登録先を解除 |
| 05 | opcode、マスクu32 BE | 現行では00000004で送信箱消去 |
| 04 | opcode、日付u32 BE、第2値u32 BE | 保存される日時関連の二値 |

22の4個の値は第1が通知フラグ、第2が旧テンプレートID相当、第3と第4が最小と最大の表示時間。サターンの受信経路では第2値を読み捨てる。現行は第2値0000を維持する。

時間外の現行例は `22 00 01 00 00 00 78 01 2C [本文長u32 BE] [strz] 02`。表示時間の値を実時間の秒と断定しない。表示には選択ユーザーや通常メニューの通知マスク等の条件もあり、22を受理しただけで画面表示完了とは扱わない。

02受信の終了値FED3を上位処理が正常終了へ変換する。一般読取失敗のFED2とは区別する。サーバーが意図的な通信エラーを起こして待機終了本文を表示させる設計ではない。

0Dは時間帯設定ではない。解除後に同じ受信番号を処理する全体挙動や、当時の用途は未確定なので、時間外拒否用に送らない。

05による共有送信箱消去は、サーバーが要求全体を保存した後に準備する。全4枠の送信箱に作用するため、一部だけ保存して送らない。ゲームDISC(ROM)の配送完了や受信側の既読ACKではない。

メール日付の現行符号化は `年 << 16 | (月 - 1) << 12 | 日 << 7`。JSTで登録日を算出し、低位7ビットは0とする。その意味や第2値の一般的な単位は未確定。実験用04の固定日付と、配信メールの登録日を混同しない。

## 11 ユーザーとメール形式

1端末に0から3の4枠があり、受信箱は選択ユーザーごとに8件。共有送信箱には別枠の送信メールが混在する。1枠の選択名を他枠の送信者へ流用しない。接続した1枠だけに受信メールを返し、残り3枠は各自の接続時に配送する。

メールのアカウントキーは0Bプロフィールの申告8バイト端末IDと枠。全0または全FFの未登録IDは正規化電話番号と枠へフォールバックする。これは利用者認証や正式なID割り当てを再現する機能ではない。

配送件数はmax(0, 8 - 申告受信件数)。配信メールを通常メールより先に入れ、余ったメールはサーバーに残す。サーバー保管総数に固定件数上限を設ける方針ではないが、ディスクやプロセス資源まで無限とは保証しない。

受信コマンド1Eはopcodeと件数u16 BE、その後に以下のレコードを件数分並べる。

| 順序 | フィールド | wireの幅 |
| --- | --- | --- |
| 1 | allocationBasis | u16 BE |
| 2 | opaqueHeader | 8バイト |
| 3 | opaqueAとopaqueB | 各u8 |
| 4 | opaqueC、アイコンID | u16 BE |
| 5 | field1、住所 | u8長とstrz |
| 6 | field2、差出人名 | u8長とstrz |
| 7 | opaqueD | u16 BE |
| 8 | opaqueE、日付 | u32 BE |
| 9 | field3、件名 | u8長とstrz |
| 10 | field4、本文オブジェクト | u16 BE長とバイナリー |
| 11 | 付加データ長 | u32 BE、現行は0 |

住所を先に、名前を後に送る。ゲームDISC(ROM)のメール本体+0x10が住所、+0x32が名前。v52の逆順はv53で訂正し、実画面で確認した。既にゲームDISC(ROM)に保存された誤順序メールは自動修復しない。

文字列の長さはNUL込み。住所と差出人は各0x22バイト、件名は0x23バイト以内の非重複制約を検査する。これは安全な符号化上限であり、歴史的な最大入力文字数を断定する値ではない。allocationBasis + 4が0x80以上0x7FFF以下、本文が確保領域に収まることも検査する。

応答に格納したメールはprepared_unconfirmedとして提示済み扱いにし、自動再送しない。ゲームDISC(ROM)の受信、既読、永続保存を確認した状態ではない。ゲームDISC(ROM)が同じ送信メールを再提出した場合は別投稿になる。アプリケーション側の再送判断をサーバー独自の配送ACKで置き換えない。

## 12 センター配信とポイント

センター配信は管理者が件名と本文、対象を登録し、対象ユーザーの次回接続で配送する。差出人はXBAND、住所は東京。全ユーザーは将来初めて接続するユーザーも含む。電話番号の全4枠または1枠への指定は現行の拡張である。

アイコンID201、ゲームDISC(ROM)リソース0115:00C9を参照する。32×56、4bppのゲームDISC(ROM)内画像であり、旧ソース画像やゲームDISC(ROM)画像をリリースに同梱しない。センターのopaqueBは0。動画の青い背景の原因は特定済みとは扱わない。

配信本文の非圧縮オブジェクトは次の形式。

```text
flags u16 BE = 0
EUC-JP本文長とNULの合計 u16 BE
checksum u16 BE = 0
本文とNUL
割当パディング u8 = 0
```

全体は本文バイト数+8。allocationBasisは0x80+全体長-4、opaqueDは0x80+全体長。件名32、本文240 EUC-JPバイト以内。日本語は通常2バイト。改行はLFへ正規化し、NUL、絵文字、非標準JISや不要な制御文字を拒否する。通常ユーザーメールの128バイト本文オブジェクト制限とは別。

サンプルメール作成ボタンは歴史的な文面を編集欄へ入れるだけ。配信先を変更せず、自動登録もしない。日付は現在の登録日であり1998年へ偽装しない。

ポイント台帳は電話番号、ユーザー枠、ゲームID別。メールのID識別とは異なる。開始値は0で、固定テスト値100を継続配信しない。勝者と敗者の配点はゲーム別に0から999、勝者-1は両方のサーバー加算なし、引き分け0。対戦開始時に設定を固定し、後からの設定を過去の結果へ適用しない。

32の00B4と00B5は自分と相手の勝利時の価値表示であり、勝者と敗者の付与先ではない。両方へ勝者の値を送り、敗者加算はサーバーの結果照合と累積25で反映する。

25は `25 [resourceID u16 BE] [本文長u16 BE] [本文] [00 00 00 00]`。本文はゲームID u32 BE、ユーザー枠u8、00 u8、ゲーム名strz、現在ランクstrz、累積ポイントstrz、次ランクstrz、必要ポイントstrz。resourceIDは枠×64+ゲームslot。現行の台帳経路は4枠分を返す。

ランクは30段階、初期閾値0、200、400から5800まで。閾値は厳密な昇順で最初0、最大999999999。単位はLEVEL、段、級からゲーム別に設定し、昇順または逆順の表示を選ぶ。30ランクと一律200幅は現行の設定可能な初期方針であり、全ゲームの当時の条件を解明した結果ではない。

## 13 対戦結果と保存先

ゲームDISC(ROM)送信20／23の84バイトは端末共通の結果資源から報告される。通常20はリソース012A:0からの結果で、異常・未完了23も同じサイズの生ブロックを扱う。現在選択しているユーザーが結果の所有者とは限らない。次のoffsetはopcodeを除き、サイズワードを先頭とした10進値である。

| --- | --- | --- |
| 0 | 4 | ブロック長84、u32 BE |
| 4 | 4 | ゲームID |
| 8 | 4 | game_error |
| 12 と16 | 各4 | 自端末側の2プレイヤー結果値 |
| 20 と24 | 各4 | 相手側の2プレイヤー結果値 |
| 28から83 | 56 | 未確定部分、生データ保存 |

現行は直近の実際の対戦回線の参加者と開始時の配点、切断を照合して付与先を選ぶ。22で対戦して21からメール接続しても、報告者21と参加者22を別に記録し、照合できた22へ加算する。実画面での確認あり。複数の古い未送信結果の一意な帰属は保証しない。

正常結果だけを既存ポイント計算へ使う。自端末2値の合計と相手2値の合計を比較して配点を選ぶが、この比較を各ゲーム固有の勝敗ルールの解明とは呼ばない。相手からの報告だけで未報告端末へ加算しない。

端末共通の未送信20結果は、ディスクや選択ユーザーを切り替えた後の接続でも報告される。結果内ゲームIDと現在の0B登録ゲームIDの相違だけでは通信を切断しない。加算・重複判定には結果内ゲームIDと既存の参加者照合を使い、現在のゲームへ過去タイトルのポイントを流用しない。25の表示更新とマッチングには現在の登録ゲームIDを使う。異なる場合は履歴のreporting_gameへ登録ゲームIDを別記録する。未設定の結果ゲームや照合不能の報告は加算せず、生結果のDB保存対象とする。この取扱いは実際のタイトル切替報告に対する現行サーバーの方針であり、旧本番サーバーの仕様を断定するものではない。

結果DBはSQLではなく追記専用JSON。生データ84バイト、SHA256、報告ユーザー、照合ユーザー、参加者、対戦接続ID、監査と台帳受領記録を関連付ける。game_errorが非0でもDBには残すが、そこからポイントを加算しない。play_timeとunitはnullのまま。旧ソースの同名フィールドを推測位置へ当てはめない。

同一電話番号、生データhash、直近観測回線、照合回線、監査ID、台帳IDが一致する報告は再保存しない。後で照合情報が追加されたら新しい版を追記する。両端末の報告は別行で、相互一致した単一確定試合DBではない。旧試合を推測して遡及登録しない。

管理画面にはメール履歴、センター配信、アクセスと対戦とポイントの履歴、対戦結果DBを分けて置く。結果DBは最新順50件、1秒更新、JSON詳細付き。中継1→2と2→1の文字列表示はASCII可視文字を表示し、その他を\\xHHで示す。日本語本文やゲームデータの意味を自動復号した表示ではない。

共通の消費度数設定では候補保存と自動消費の明示有効化を分ける。手動の一回限り消費試験は通常料金とは別で、通常の自動消費と重ねない。モデムの登録電話番号表示はゲームDISC(ROM)から取得・検証した値だけを使い、未取得なら `Not yet reported` と表示する。昔の固定テスト番号を表示の既定値へ戻さない。内部の仮想対戦番号は別のルーティング情報として保持する。

定期描画によるボタンのちらつき対策は子領域の背景塗り潰しと不要な再配置・フォント再設定を抑止する。ボタンの操作と通信更新周期を変える機能ではない。

## 15 全タイトル共通の度数とメディアカード

### 15.1 料金設定と適用範囲

度数はメディアカードの残数であり、勝敗で増えるXBANDポイントとは別である。全電話番号・全ユーザー・全ゲームに同じ処理と料金を適用する。ゲーム別料金表やタイトル別リセット条件は設けない。ゲームIDは対戦と結果を正しく結び付けるために照合する。

| サービス | 標準の消費度数 | 設定と精算時期 |
| --- | --- | --- |
| メール接続 | 1 | 全体で0～32767に設定。明示有効化後、その接続のサービス応答前に消費 |
| 正常対戦 | 3 | 全体で0～32767に設定。対戦開始時に金額を固定し、終了後の新しい結果付き接続で精算 |
| 途中リセット | 各側1 | 両参加者の対戦分を1に置き換える固定方針。通常対戦額にさらに1を加える仕様ではない |
| 対戦精算時のメール | 上記メール料金を加算 | メール接続の場合のみ加算。標準では正常対戦後4、リセット後2 |

0～32767は実装の検証済み要求範囲であり、当時の料金設定上限ではない。設定なしの初期状態ではメール・対戦の自動消費は無効。管理者が明示的に有効化するまで、標準値を保存しただけでカードを消費しない。

設定は `schema:3`、`scope:"server-global"`、`activation:"explicit-service-policy"`。`mail_enabled` と `match_enabled` でそれぞれ有効化し、`requested_units.mail`／`match` に共通料金を保存する。`requested_units.reset:1`、`reset_scope:1`、`include_mail:1` は固定方針。旧schema1候補設定は無効のまま読み込み、旧schema2のメール専用設定から対戦消費を勝手に有効化しない。

### 15.2 端末別の精算フロー

対戦開始時に両端末の参加者、カード、直前結果、共通料金を保存する。対戦後の最初の新しい結果付き接続で、その端末自身の結果・カード・帰属を照合し、49を一度だけ送る。相手端末の接続・結果一致を発行条件にしない。後から届く相手結果は監査比較に使い、確定済み金額を再計算しない。

通常20・game_error＝0・非ゼロの対戦カウンターは固定された通常料金を使う。異常23・−608または−609はゲームIDに依存しない共通判定でリセット料金1へ分類する。その他のエラー、古い結果、同じ結果の矛盾、帰属不能な報告、−13の未完了報告を根拠なくリセットへ読み替えない。強制終了や通信断がすべて自動的にこの報告を生成するとは保証しない。

```text
対戦開始で帰属と料金を保存
  → 各端末の次回接続で自身の新しい結果を照合
  → 49の送信意図を保存して一回送信
  → 完全な1E返信の実績とカード更新を検証
  → 精算台帳を確定
  → 許可されたメールまたは対戦サービスを継続
```

再起動時も同じカードと二つの台帳を引き継ぐ。カードが変わった、相手側へ移された、同じカード・電話に未解決の消費がある場合は、自動で別料金へ置き換えず停止する。消費台帳だけ確定した直後のクラッシュは保存済み返信と現在カードが一致する場合に受領状態を復旧し、同じ対戦分を再請求しない。

### 15.3 カード挿入とゲームDISC(ROM)による消費

ソフトウェア上の有限カードは既存13バイトファイルを指定して挿入する。Ymir移植版のシリアルポート設定またはモデムの挿抜APIが入口となり、挿入時に度数を自動補充しない。実カードのモデム挿入口へ物理的に挿した動作を検証したものではない。

カードの先頭8バイトは識別の照合に使い、後続5バイトのビット数を基数8で畳み込んだ値が残数となる。通常の整数を13バイトへ書き込む仕様ではない。サーバーは申告を受けて要求額を送るが、残数をサーバーだけで直接減算しない。ゲームDISC(ROM)の既存49処理がカードを更新し、更新データと実消費を返信する。未挿入の長さ0と、有限の長さ13を区別する。負の申告値や無限扱いを有限カードの正当な消費実績としない。

| 方向と文脈 | wire形式 | 全長 |
| --- | --- | --- |
| 登録時のゲームDISC(ROM)カード申告 | `1E 00 [残数 signed BE16] [長さ BE32] [raw]` | 8または21バイト |
| サーバーの消費要求 | `49 [要求量 BE32] [照合長 BE32] [照合データ]` | 現行の13バイト照合では22バイト |
| ゲームDISC(ROM)の完全な消費返信 | `1E 00 [更新残数 signed BE16] [長さ BE32] [raw] [実消費 signed BE32]` | 12または25バイト |

現行の自動精算は有限カードの完全なデータで照合する。通常確定には要求量と実消費、初期残数−更新残数、先頭8バイトの識別が一致する必要がある。49の原ゲームDISC(ROM)処理に取引IDによる重複排除はなく、返信がないからと同じ要求を送ると二重消費し得る。

### 15.4 不足と結果不明の扱い

未精算の対戦分を優先し、メール分まで足りなければメールを行わない。残3で通常対戦後のメール接続なら対戦分3だけを要求し、残0としてメールを停止する。残2に通常対戦分3を要求した確認では、ゲームDISC(ROM)は実消費2・残0を返した。負の残数を保存するのではなく、条件を満たす使い切り実績を `exhausted` として記録し、同じ対戦分を再請求しない。対戦開始前に最低3度数を一律要求する制約は追加しない。

残0などの不足案内は確認済み22＋02を使う。要求量・実消費・残数を表示する現在の本文は運用用の追加であり、旧日本サーバーの文面や−505応答を復元したものではない。案内後はメールの送受信・対戦接続を進めない。

タイムアウト、消費後の返信欠落、実績不一致、カード識別変更は `uncertain`／`blocked` として新しい自動消費を止める。自動再送・差額消費・返還・補充は行わない。後段サービス失敗を消費取消の根拠にしない。手動の一回限り試験や旧レビュー予約がその接続を所有している場合、自動料金を重ねない。

### 15.5 確認結果と史料の範囲

2026年10月9日の共通化後の操作試験では、VF REMIX原ゲームDISC(ROM)と合成有限カードで左右ともメール90→89、正常対戦後89→85、途中リセット後85→83を確認した。消費台帳は各要求1／4／2に対して実消費も1／4／2、状態confirmed。途中でゲームを閉じて再起動しても89を保持し、前回分を重複請求しなかった。現在の試験カード残数は両側83であり、配布用の初期カードを意味しない。

利用者提供のWorld Wide Soccer 98、Sega Rally、VF Remix、Virtual-On for Sega Netのマニュアルは基本料金のメール等1・対戦3を裏付ける。World Wide Soccer 98とVirtual-Onは次回通信時の差引きやリセット時1も記載する。両側リセット1・メール加算・全タイトル共通という適用方針は利用者指定を含む現行仕様であり、すべての当時の例外を解明したという意味ではない。

SNES系を含む公開旧ソースの端末別結果精算・不完全消費・後続サービス停止は参考にするが、接続前減算や再接続補償をSaturnへそのまま移植しない。実メディアカードの物理動作と、SNES製品ゲームDISC(ROM)を実行した度数試験は未確認のままとする。

### 16.1 標準ゲーム定義と追加

アプリ標準のゲームIDとスロットは以下のとおり。仮名の項目は表示名が未確定であり、タイトル名を推測して埋めない。保存済みの管理者設定がある場合はそれを優先する。このリストは料金を分岐させる許可リストではない。

| slot | ゲームID | ソース内の標準表示名 |
| --- | --- | --- |
| 1 | 00010003 | Virtua Fighter Remix |
| 2 | 00018003 | PUYO PUYO SUN |
| 3 | 00018002 | ID 0x00018002 |
| 4 | 00010007 | DECATHLETE XBAND |
| 5 | 00010006 | DAYTONA USA CIRCUIT EDITION |
| 6 | 00010004 | ID 0x00010004 |
| 7 | 00018001 | SATURN BOMBERMAN |
| 8 | 00010005 | VIRTUAL-ON |
| 9 | 00010008 | SEGA WORLD WIDE SOCCER 98 |
| 10 | 00018004 | SHADOWS OF THE TUSK |

確認済みゲームIDの一覧は `game_ranking_settings.hpp` の `rankingDefaults()` にアプリ標準値として格納する。設定JSONなしでも一覧を構成でき、既存JSONを読み込む場合も標準定義を基に編集値を反映する。このID定義はリポジトリ・配布ソースに保持し、削除・匿名化対象にしない。個別の設定値、累積台帳、メール、通信ログとは分離する。未確認IDを推測で標準定義へ追加しない。

デカスリートは `/DECAINFO/GAMEINFO.BIN;1` の先頭BE32 `00010007`、次のBE32 `00000001`、オフセット8のタイトル `DECATHLETE XBAND` からIDを確認した。第4スロットの仮項目 `ID 0x00010007` を正式名称へ更新する。旧設定を読み込む際、仮名だけを移行し、仮名かつ上書きなしの初期配点を標準勝者1へ補う（敗者の保存値、明示設定済みの配点は保持）。ID・スロット・累積台帳は変えない。正式名の設定や編集済み配点は変更しない。移行内容は設定画面で保存するとJSONに永続化される。

SATURN BOMBERMAN（日本SegaNet版）の `/XBAND/GAMEINFO.BIN;1` は先頭BE32が `00018001`、次のBE32が0、オフセット8から `SATURN BOMBERMAN`。第7スロットの標準定義として保持する。旧試験設定の仮名・誤登録名の訂正と、正式名称で保存された管理者の配点は区別し、累積台帳をリセットしない。Dragon’s DreamはXBAND対象外として追加対象から除いている。

DAYTONA USA CIRCUIT EDITIONの `/GAMEINFO/GAMEINFO.BIN;1` は先頭BE32が `00010006`、次のBE32が `00000001`、オフセット8から製品内タイトル名を持つ。第5スロットの旧仮項目 `ID 0x00010006` を正式名称に置換した（別IDとして追加しない）。新しい起動用コピーでは旧仮名かつ上書きなしの初期配点だけを標準勝者1・敗者0へ変更し、その他の保存済み配点と累積は保持する。通信要求でのID照合は実接続時に継続する。

Shadows of the Tuskは両端末の実接続ログでゲームID `0x00018004`（98308）を確認し、第10定義に追加した。名称は `SHADOWS OF THE TUSK`、初期配点は勝者1・敗者0、ランク初期方針は他の新規ゲームと同じローカルLEVEL・200刻みとする。過去の配点・ランク条件を確定したという意味ではない。旧8／9タイトルの設定ファイルは編集値を保持して読み込み、新定義を補う。

ゲーム・勝者／敗者ポイント設定画面の下部で、新規ゲームID（16進数、`0x` 接頭辞は任意）とゲーム名を入力し「ゲームを追加」で永続保存できる。IDは実際のゲームDISC(ROM)要求と一致させる必要があり、登録だけでゲーム自体のネット対戦対応を保証しない。空名・非対応文字・重複ID・0・FFFFFFFFを拒否する。各ユーザーのコマンド25資源IDは `user*64 + slot` であるため、スロット1～63、最大63ゲームとする。追加したIDとスロット順は再起動後も維持する（削除・ID変更機能はない）。

World Soccer ’98（`0x00010008`）は標準の第9定義に追加した。旧8タイトル設定ファイルは既存編集値を保持して読み込み、第9定義を補う。新規ゲームは「サーバー設定の配点を適用」を初期選択とし、標準配点の勝者1・敗者0ポイントを使用する。これはサーバーの設定値であり、固定の累積テスト値や当時の公式配点ではない。保存済みの個別配点や明示的な「上書きなし」は変更しない。ランクは共通のローカル初期方針LEVEL・30段階・200刻みであり、当時の公式条件ではない。追加後は勝者／敗者値と昇格条件画面の閾値・表示単位を変更できる。未知の独自ゲームもランク条件を別ファイルに保存・復元する。既存ユーザーの累積は変更しない。

ゲーム名・ランク設定の欠落を通信失敗にしない。旧SegaServerの `Server/Server_StartGamePlay.c` はゲーム名DB検索に失敗すると `gameName[0] = 0` とし、通常の待機登録送信へ進む。本実装も名前を空文字として既存のSaturnコマンド22による待機案内と0Eによる期限、終端02を維持する。指名待機では従来どおり22を追加しない。未知IDのタイトル008B、ランク25、付与値の上書きは行わない。サーバーログに `STANDBY_TITLE_MISSING` を残す。要求形式や待ち時間値の不正を黙って受理する変更ではない。

World Soccer ’98の実要求でID `0x00010008` を観測した。定義追加前にこのIDと合成未知IDで欠落経路を検証し、追加後は未登録の2IDに変更して左右・4ユーザー・指名/自動の32ケースで回帰試験する。10定義の待機経路は480ケースで検証する。実画面での待機と対戦は別途確認する。

旧ソースの `Server/Server_UpdateGamePatch.c` にある真の未対応ゲーム通知・`disallowGameConnect` は、表示用定義欠落とは別の判定である。これはMegaDrive系旧ソースであり、Saturn版の同等コマンドは未特定のため、推測で応答コードを移植しない。待機通知の文面・時間見積もりは現行互換実装の既存方針であり、旧サーバーと完全同一という主張ではない。
