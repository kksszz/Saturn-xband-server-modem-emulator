# 混在メールの保存後消去：隔離実験

## 対象と注意

既知のVF REMIX制御05／mask04は、選択中プレイヤーだけではなく、全4プレイヤーの送信待ちを消す。個別消去として使わない。

本実験は新規COW・単一ゲスト・同一実行範囲・観測済み0／3の混在2件だけに限定する。通常配布版ではOFF。番号1／2を含む要求、3件以上、送信中の保存状態置換、別PC実試験は対象外。

## 初心者向けの動作順

1. 元ゲームからメール専用要求04を最後まで受信する。
2. 送信リスト1Dを構造通りに読む。本文から命令らしい値を検索しない。
3. 出所番号ごとに、その端末・同じ保存環境で観測したコードネームを照合する。不明なら要求全体を保留する。
4. 保管ストアのコピーに全件を入れる。容量不足や途中の不正データでは元ストアを変更しない。
5. 全件入りのコピーをスナップショットへ保存する。Windows側アダプターは新規.pendingへ書く→FlushFileBuffers→MoveFileExWのwrite-through置換を使う。エラーなら消去を返さない。
6. 保存成功後にRAMストアと受付IDを公開する。
7. 今回受付がちょうど2件で、出所順が0／3、実行範囲が有効、今回の保存完了が確認できた場合だけ消去を準備する。
8. 現在の受信箱へのメール返信に、既知の消去05と最後の02を続ける。

サーバーが「消去を準備した」ことと、ゲームが実際に消したことは別。元ゲームの次回送信リストが空か、受信済みメールが残るかを実試験で確認する。

## 制御のバイト列

```text
05 00 00 00 04 02
```

|部分|意味|
|---|---|
|05|観測済みのゲーム側制御ハンドラー|
|00 00 00 04|32ビット・ビッグエンディアンのmask04。送信待ち全件の消去|
|02|メール交換の終端。配達証明ではない|

受信メールがあれば、既存の1E返信の末尾02をこの6バイトに置き換える。0／3の実要求560Bに対応する試験では、受信2件の98B返信に5B増えて103Bになる。05は本文や各メールのIDに埋め込まない。

## 設定と責任の分離

診断サーバーの `XBAND_MAIL_PROFILE_BATCH_CLEAR_EXPERIMENT=1` と `XBAND_MAIL_PROFILE_BATCH_SNAPSHOT_FILE=<新規の絶対パス>` を使う。ProfileNames／ProfileMailbox／ProfileInventoryも必須。

試験ラッパーの指定は `-ProfileBatchClearExperiment`。結果フォルダ内の新規 `profile-batch-custody.xbm` を選び、終了時に試験環境変数を元へ戻す。

- 従来の `ClearOutgoingExperiment`／`InventoryExperiment`／`PersistMailExperiment` とは別。併用しない。
- 同じ専用保存ファイル、既存.pending、復元モードを認めない。既存保存を上書きして新規実行の番号表へ混ぜない。
- 単独1件は保存するが消去しない。同一番号の2件、空要求も、この新設定では消去しない。
- 不明な出所、保存失敗、容量不足、外側TCP切断後の範囲無効化では消去しない。
- `batch_clear_experiment` のenabled／prepared／snapshot_committedを各モデムのステータスJSONへ出す。直近のサービス要求の状態であり、実際の消去完了を表す値ではない。

一括保管とスナップショット形式は独立C++20部品。Windowsへの書込みはファイルアダプター、元ROMの1D／1E／05変換と許可条件は診断サービスアダプターで扱う。Ymir本体やモデムのゲスト実行へ新しい消去コードを埋め込まない。移植先では、全送信待ちを列挙する範囲と消去範囲の一致をその機種で確認する必要がある。

## 保存・再送の限界

保存形式は既存XBMAIL v1。保管ID、出所端末・電話番号・コードネーム、元プレイヤーprefix、宛先・件名・本文・suffixを含み、CRCで破損を検査する。CRCは認証ではない。

今回のファイルには、名前表の実行範囲・提示履歴の自動復元はない。書込み後の保存内容を読み取り専用で確認できるが、通常サービスの自動復旧機能としては使わない。

保存成功からゲームが消去を処理するまでに切断すれば、同じメールが再提出される可能性は残る。新しい提出を本文一致だけで消さない。保存への受付、相手への返信、相手での保持・読了は別であり、厳密な一度だけの配達や正式な受領証明は保証しない。

## 検証

サービス試験は元524／560B記録を使い、両端末の混在保存後の正確な103B返信を確認した。模擬保存失敗、容量不足、不明な出所、範囲無効化、単独要求、保存処理なしでの設定拒否を検査した。これらは元ゲームが送信待ちを消したという証拠とは分ける。

元ゲームの試験結果は `../../outputs/ymir-xband-investigation/` の実試験記録へ記載する。

2026-09-29の元VF REMIX試験では、単独1件は保存だけ、次の混在0／3の2件は全保存後に消去。後続の原版要求489／491Bは送信待ち0件で、0の受信一覧は1行を維持し、保持1003の再提示も抑止した。保管3件142B・ファイル198Bは残る。厳格検査PASS、36000フレーム完走。これは観測した新規0／3環境のみで、番号1／2や通常復旧まで成功したという結果ではない。詳細は `../../outputs/ymir-xband-investigation/vf-mail-profile-batch-clear-20260929.md`。
