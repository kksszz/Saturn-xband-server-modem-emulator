# プレイヤー別の提示番号と受信保持情報

## 何を防ぐ仕組みか

受信したメールを次の接続でもすべて返すと、同じメールの行が増える。元VF REMIXは受信レコードの2バイト値を次回接続で報告するが、従来の仮値0089は同内容の2レコードで重複したため、一意IDにはできない。

隔離した診断実験では保管IDから合成した番号を返し、次回その番号が報告されたら、以前そのプレイヤーへ提示したメールに限って今回の返送から除く。送信待ち消去、既読・配達確認、正式認証とは別の機能。

## 動作順序

1. 完全なメール専用要求04から、現在番号0／3と受信保持word一覧を読む。
2. 診断word1001～1080を保管ID1～128へ変換する。
3. 端末・制御された観測範囲・現在のプレイヤーが一致する提示履歴で照合する。未知、他プレイヤー、未提示のIDは採用しない。重複値は1件にまとめる。
4. 宛先が現在のプレイヤーに一致する保管メールだけを対象に、上記の保持IDを除外する。
5. 残る候補を保管順に最大4件選ぶ。
6. 受信1EのopaqueDへ `0x1000 + localId` を入れた応答を作る。他の本文・確保サイズ等は既存の変換規則のまま。
7. 提示履歴を一括登録できた場合だけ応答へ入れ、最後に02を返す。

「提示」は返信候補を用意したという意味で、TCP送達や元ゲームの保存・読了を保証しない。報告も未認証の診断データであり、悪意ある相手に対する防御や正式な配達証明ではない。

## 独立部品のAPI

`include/xband/mail_profile_offers.hpp` はC++20標準ヘッダーだけの部品。Ymir、Windows、GUI、ネットワーク、ゲームDISC(ROM)上の形式に依存しない。

```cpp
xband::MailProfileOffers offers; // 同じ保管ストア・実行範囲で共有
auto validated = offers.heldFor(currentProfile, reportedCustodyIds);
auto selected = xband::selectProfileMailbox(store, names, currentProfile, 4, validated);
// selectedから本文と応答を作り、preparedCustodyIdsを集めた後：
const bool accepted = offers.offerBatch(currentProfile, preparedCustodyIds);
// acceptedの場合だけ応答を公開する。拒否時は受信メールを返さない。
```

登録は全件成功か全件拒否。同じID・同じ宛先の再提示は許容し、別宛先への同じIDの再割当、容量不足、範囲外キーは拒否する。既定128件、入力の保持IDも最大128件。ゼロIDは不正。IDから端末・観測範囲・ローカル番号を記録するため、どれか1つが違えば保持対象にならない。

現在の保持報告を照合する前に今回の新着候補を提示表へ登録してはいけない。新着の番号を報告しただけで、まだ提示していないメールを除外できてしまうため、上記の順番を守る。

ゲームDISC(ROM)のword変換は診断アダプター `diagnostic_mail_inventory.hpp` が担当する。移植先の受信形式が違っても、対応する検証済み保管ID一覧を作れば独立部品は再利用できる。1つの提示表を別の保管ストアへ使い回してはいけない。

## 設定と寿命

追加設定 `XBAND_MAIL_PROFILE_INVENTORY_EXPERIMENT=1`。実行ラッパーは `-ProfileNamesExperiment -ProfileMailboxExperiment -ProfileInventoryExperiment` を使用する。新規COW・単一ゲスト・単一サーバー実行に限定。

- 従来の `-InventoryExperiment` ではない。全員分送信待ち消去、Forward、Snapshot、サーバー再起動とは併用しない。
- 既定はOFF。通常配布パッケージでは有効にしない。
- 外側のモデムTCP接続が切れたら提示表を空にし、プロファイル実行範囲を無効化する。同じサーバーへの再接続で古い保管を新保存環境へ移さない。
- 電話サービスの終了・再発信では提示表を維持する。
- 永続化なし。状態ロード、既存セーブの再利用、プロファイル置換は対象外。
- `inventory_experiment` のreported／withheldをステータスへ出す。範囲は直近のサービス接続であり、履歴表の全件数・既読数ではない。

別設定の混在保存後消去実験 `MAIL-PROFILE-BATCH-CLEAR.md` は、専用新規スナップショットへ全件保存した観測済み0／3要求だけに全送信待ち消去を許可する。このInventory設定だけで消去を許可するものではなく、従来のClear／Forward／Snapshotフラグとも別。通常はOFF。

単独0／3への拡張も別設定 `MAIL-PROFILE-SUBMISSION-CLEAR.md` とする。旧混在設定と併用せず、保存完了後だけ全送信待ち消去を準備する。Inventory単独での消去権限は追加しない。

## 残る重複

送信待ちを消去しないため、元ゲームが同じ内容を再送すると新しい保管IDになる。その新IDは受信済み旧IDとは異なるので今回の抑止では除かない。本文・件数・名前の一致だけで同じメールと決めて削除しない。

今回の抑止は「同じ保管IDの再提示」だけ。送信待ちの安全な個別確定・消去、正式な一意ID、恒久的配達確認は別途必要。

## 検証の区別

部品試験は、現在番号・端末・範囲の分離、重複／未知ID、登録容量不足時の一括拒否、別宛先へのID再割当拒否、無効化を確認。
サービス試験は元524B／560B要求を基に、診断wordを挿入した模擬3回目要求で、両端末の既知2件の除外、従来0089の無視、他宛先・未提示・未知・重複番号の拒否を確認した。保管は削除せず、制御05は送らない。

元ゲームの保持・一覧表示の確認は別の実試験記録に残す。合成した保持word要求によるサービス試験だけで、元ゲームの受信・再報告成功とは扱わない。

同日の元VF REMIX試験で、プレイヤー3が診断word1001／1002を再接続時に報告し、旧ID1／2を除外、新しい再送保管分ID4だけを返すことを確認した。一覧は抑止なしの5行に対して3行。保管5件237Bは削除しない。反対側端末・番号0の保持・抑止は今回の実ゲーム対象外。詳細は `../../outputs/ymir-xband-investigation/vf-mail-profile-suppression-20260929.md`。

追加の同一起動0→3→0→3試験でも、番号3は1001／1002だけを報告し、旧ID1／2を除外、新ID4／6を受信した。番号0への初回返送ID3／5と混ざらないことを確認。番号0自身の保持報告を含む5回目は操作補正が48000フレーム上限に間に合わず未確認で、5接続検査は不合格。番号0の抑止も実ゲームで成功したとは扱わない。詳細は `../../outputs/ymir-xband-investigation/vf-mail-profile-switch-20260929.md`。

後続の補正済み入力による0→3→0→3→0では、番号0も元要求564Bで1003／1005を報告した。提示履歴の現在番号0と照合して旧ID3／5だけを除外し、新ID7／9を返送。番号3の1001／1002とは混ざらず、番号0の一覧は再接続前2行から新しい2件を加えた4行。5接続の厳格検査PASS、48000フレーム完走、保管9件427B・消去なし。番号0／3の保持報告と再提示抑止は元ゲームで確認できたが、別端末・番号1／2・既存保存環境の変更は対象外。詳細は `../../outputs/ymir-xband-investigation/vf-mail-profile-switch-success-20260929.md`。
