# プレイヤー番号と観測した名前の対応

2026-09-29の観測名対応部品。読み取り専用解析に加え、隔離した新規保存環境の診断サーバーで0／3の混在受付へ組み込んだ。通常起動や混在配送には有効化していない。以下の実測経緯と試験用の制限を参照。

`include/xband/mail_profile_names.hpp` はC++20のみで利用でき、Ymir、Windows、ネットワーク、JSONを必要としない。単一所有者から使用する部品で、スレッド同期は内部に持たない。

## なぜ必要か

VF REMIXの実送信要求では、複数プレイヤーの送信待ちメールが一緒に送られるが、解析済み登録ヘッダーの名前は現在選択中のプレイヤーのものだけだった。別プレイヤーのメールにもその名前を付けると差出人を取り違える。

対応のキーは次の3つ。電話番号をキーにしない。

| キー | 意味 |
| --- | --- |
| endpoint | サーバー側で区別したモデム端末。名前や発信番号から推測しない |
| epoch | 保存データの同一性を区別する識別子。試験用コピーや置換された保存データを混同しない |
| player | ローカルプレイヤー番号0～3。アカウント認証IDではない |

`epoch` はゲームの通信バイトに追加するフィールドではない。所有側が管理する内部キーで、今回のログ解析ではログごとに新しい表を作る。将来ライブに組み込む場合は、保存環境の置換・同一性を保証できないリセット／状態ロード時に、所有側が表を無効化するか別epochへ移る必要がある。単なる電話の切断／再接続だけから、名前の消去・再利用を判断してはいけない。このライフサイクル通知のライブ実装は未完了。

## API

```cpp
xband::MailProfileNames names; // 既定の上限128エントリ
names.observe(endpoint, epoch, player, codenameBytes);
auto one = names.resolve(endpoint, epoch, player);
auto all = names.resolveBatch(endpoint, epoch, playerIndices);
names.invalidateEndpoint(endpoint);
```

- `observe` は新規、同じ名前の再観測、矛盾、容量不足を返す。違う名前が同じキーで観測されたら、改名か保存環境の変更かを区別できないため、そのキーを矛盾状態にする。後の同じ名前の再送では復旧しない。
- `resolve` は観測済みかつ矛盾のない名前だけを返す。
- `resolveBatch` はレコード順に名前を返す。1件でも未確認・矛盾なら全体を未確定とする。部分結果を返さず、同じ番号の複数メールを勝手にまとめない。
- `invalidateEndpoint` は対象端末の全epochを削除する。他端末の対応には触れない。
- 端末／epochは空でない64バイト以下、埋め込みNUL不可。名前は空でない32バイト以下でNULを含めない。Shift-JIS等の元バイトをそのまま扱う。番号は0～3、バッチは128件以下。

この部品は名前の対応だけを担当する。メール保管、ID発行、配送、課金、認証、元ゲームの送信待ち消去は行わない。名前がすべて解決したことだけを配送／全員分消去の許可にしてはいけない。

## 現在の実測範囲

読み取り専用ツール `outgoing_list_survey` の `--inspect-player-prefix --resolve-current-profile` で登録名を学習し、各レコードとの対応と全体の確定可否を表示する。各ログは独立した表で解析する。

混在0／3の実ログでは、現在の3は「新規プレイヤー9978」と解決し、0は未確認のため全体保留。独立した以前の0の試験で使った88を、このログへ持ち込んではいけない。単独プレイヤー0の2件ログでは両件88、単独1のログでは99と読み取り専用で解決した。1／3のライブ受付を有効にしたわけではない。

部品試験の、同じepoch内で0と3を両方観測して全件を解決するケースは模擬データ。元ゲームで同じ保存環境の両登録を連続観測する試験は次の課題。

同日追記：元VF REMIXの同一保存環境で0＝88を先に通信で取得し、その後3＝99を登録した混在2件要求を取得した。1回目524B→2回目560Bの連続履歴で全件対応がPASS。`mail_profile_sequence_survey` は1つの制御された単一端末・同一保存環境のログだけを読み、`--require-resolved-mixed` で全件対応した混在要求の存在を検査できる。2台参加ログは拒否する。任意ログから保存環境の同一性を証明するものではない。ライブへの組み込み・配送は未完了。詳細は `outputs/ymir-xband-investigation/vf-mail-profile-sequence-20260929.md`。

## 隔離した診断サーバーへの組み込み（同日・次の段階）

`XBAND_MAIL_PROFILE_EXPERIMENT=1` のときだけ、元VF REMIXで確認した番号0／3・最大2件の送信形式を受け付ける。既定はOFFで、1／2や3件以上のライブ対応は拡張していない。`run-dummy-mail-integration.ps1` の `-ProfileNamesExperiment` は、Capture＋EmptyMailboxの単一ゲスト試験だけで使用できる。

制限：

- 毎回、新しい試験用保存環境と新しいサーバーを使い、同じ起動中に元ゲーム内でプレイヤーを切り替える。既存セーブの再利用、状態ロードや保存環境の置換は禁止。
- Forward、Clear、Inventory、Snapshot、サーバー再起動の実験とは同時使用できない。ゲームの対戦要求03もこのモードの対象外で、メール専用要求04だけを扱う。
- 名前表はサーバー所有で、端末ごとに分離する。内側の電話サービスの切断／再発信では維持し、外側のモデム接続が切れたら対象端末分を無効化する。
- ライブの現在番号43は観測上のローカル番号としてのみ扱う。未知の名前、同じキーの矛盾、表の容量不足では全件を保留し、IDや消去権限を発行しない。
- 全件の名前が確定してから `MailCaptureStore::retainBatch` で一括保管する。保管の途中容量不足等でも一部だけ残さない。
- 同じ送信待ちが再送された場合、元形式に確定した一意IDがないので別の保管IDを割り当てる。消去しない試験では先のプレイヤー0のメールが再び混在するため、初回1件＋次回2件＝3件になり得る。
- 返信は既存の02のみ。受付IDは内部の観測番号であり、元ゲームの受領・配達確認ではない。保管はメモリのみで、サーバー終了時に消える。

通常運用で必要な状態ロード／保存環境置換の通知は未実装。そのため、この試験設定を一般利用へ有効化してはいけない。名前対応だけを理由に配送を始めず、宛先も端末＋プレイヤー番号で安全に区別する設計が別途必要。

同日実ゲーム確認：上記設定で元VF REMIXの524B→560B要求を全件保管し、ID1／2／3・3件142B・名前表2件、応答02のみ、エラーなく一覧へ戻ることを確認した。30000フレーム完走。混在配送や通常配布版の有効化ではない。詳細は `outputs/ymir-xband-investigation/vf-mail-profile-admission-20260929.md`。
