# 選択中のプレイヤーだけへメールを返す仕組み

## 目的と範囲

モデム1台の中に複数のプレイヤーがいる場合、端末だけで宛先を決めると別の人の受信箱へ入れてしまう。そのため、観測した宛先を **端末・保存環境の範囲・プレイヤー番号** の組で扱う。

今回の実装は、新しい保存領域で起動したVF REMIXのプレイヤー0／3向けの隔離試験。通常起動は変更せず、歴史的な認証・配達確認・カード課金・送信待ち消去も実装しない。

## データを受け渡す順番

1. 元ゲームの登録ヘッダーから、現在のプレイヤー番号候補と登録名を観測する。
2. 送信待ちの各メールに、実際に観測した差出人名を対応付けて一括保管する。
3. 保管メールの宛先名を名前表で検索し、宛先が1組にだけ対応することを確認する。
4. その組が、いま接続している端末・保存環境の範囲・プレイヤー番号と一致するメールだけを選ぶ。
5. 選んだメールを既存の実験用1E形式へ変換し、最後に02を付けて元ゲームへ返す。

例：同じ端末で0＝88、3＝99を観測した場合。

| 選択中のプレイヤー | 返す宛先 | 返さない宛先 |
| --- | --- | --- |
| 0（88） | 88 | 99、未確認の名前 |
| 3（99） | 99 | 88、未確認の名前 |

返信を用意したことと、元ゲームが受信・表示したこと、配達確認を得たことは別。既存の1E変換の日時等の不明フィールドは合成値のままで、今回解読できたものではない。

## 部品APIと移植

`include/xband/mail_profile_mailbox.hpp` はYmir、Windows、通信、JSONに依存しないC++20部品。

```cpp
xband::MailProfileNames::Target current{endpoint, epoch, player};
auto selected = xband::selectProfileMailbox(store, names, current, 4);
```

戻り値は一致件数 `matched`、返送候補 `prepared`、上限を超えて残した件数 `deferred`。保管順で最大4件を選ぶ。同じ本文でも重複排除しない。選択後も保管は削除しない。

同日・次段階：第5引数へ、アダプターが現在の端末・観測範囲・番号に対して検証済みの保管ID一覧を渡せる。該当宛先に限って一覧にあるIDを今回の応答から除き、`withheld`へ数える。除外後に応答上限を適用するため、既に持っているメールで新着の枠が埋まらない。重複ID・未知IDは件数合わせに使わず、宛先違いのメールには影響しない。

```cpp
auto selected = xband::selectProfileMailbox(store, names, current, 4, validatedHeldIds);
```

これは保管IDの選択規則であり、元ゲームのopaqueな2バイト値をIDへ変換する処理ではない。原版の仮値0089などをそのままこの引数へ渡してはいけない。既定の空一覧では前回と同じ返送候補になる。後続の隔離設定 `XBAND_MAIL_PROFILE_INVENTORY_EXPERIMENT=1` では、同じプレイヤーへ提示済みの診断番号と照合してからこの第5引数を利用する。詳細は `MAIL-PROFILE-INVENTORY.md`。受信済み判定による保管の消去・配達確認・同内容再送の重複排除はしない。

`names.uniqueTarget(epoch, recipientBytes)` は、指定された観測範囲の中で宛先名が1組だけに対応するときだけ結果を返す。同名が別の番号・端末にある場合は未確定。名前表に矛盾が1つでもある観測範囲では、古い名前の取り違えを避けるため返送を全体的に止める。

移植先は、元エミュレータの読み書きから登録名と選択番号を取得するアダプター、保存環境の変更通知、1E相当の受信形式への変換を担当する。受信先選択そのものにYmirのRAMアドレスやフレーム待ちは含まれない。

今回の `epoch` は診断サーバーの1回の制御された実行範囲（`fresh-COW-server-run`）。端末は別キーで区別する。任意の過去ログや別実行から名前を混ぜない。別PCに展開する場合も、サーバー側で同じ有効な観測範囲に参加する端末を管理し、各PCの保存データが変更されたらその範囲を無効化する必要がある。PCごとのローカル番号だけを宛先IDにしてはいけない。別PC実試験は今回の対象外。

## 試験設定

`XBAND_MAIL_PROFILE_EXPERIMENT=1` に加えて、明示的に `XBAND_MAIL_PROFILE_MAILBOX_EXPERIMENT=1` を指定する。実行スクリプトでは `-ProfileNamesExperiment -ProfileMailboxExperiment`。

- 新規保存環境・新規サーバー・単一ゲストのメール専用要求04だけを対象とする。
- 従来の `XBAND_MAIL_FORWARD`、Clear、Inventory、Snapshot実験とは併用しない。
- 通常起動では新しい受信先選択を使わない。
- 元形式の一意IDが未確定なので、再接続で同じ送信待ちが再保管され、同じ受信内容が複数行に増える場合がある。
- 保管はメモリのみ。サーバーを終了すると失われる。

外側のモデム接続が切れたら、名前表の該当端末分を無効化し、サーバー実行範囲全体も無効にする。再接続で同じ名前が登録されても、古い保管メールを新しい保存環境へ自動移行しない。続けるには新規保存環境・新規サーバーの試験を開始する。電話サービスだけの終了／再発信では範囲を無効化しない。

保存環境変更・状態ロードを一般運用から自動検出する通知は未実装。そのため、この設定は通常配布版に有効化しない。原版の全プレイヤー送信待ち消去も無効のまま。

## 検証の区別

続く元ゲーム試験では、同じ起動環境で0→3→0の3回の実要求524／560／560Bを取得した。3の受信一覧には88の2行、0の一覧には99の2行を表示し、実ログでもそれぞれ保管ID1／2と3／5だけを返した。詳細は `../../outputs/ymir-xband-investigation/vf-mail-profile-mailbox-20260929.md`。本文の新たな画素一致、配達確認、重複抑止は今回の確定結果に含めない。

元ゲーム試験の終了時には、外側接続の切断と名前表無効化を実ログで確認した。途中で意図的に外側切断して再接続する追加試験は行っていない。

部品試験では端末・プレイヤー・観測範囲・上限・順序・未知・同名・矛盾による拒否を確認した。サービス試験では元ゲームの524B／560B要求を使い、3に99宛のメールだけを返すことを確認した。0への逆方向返送は、最初のサービス試験時点では現在番号と名前を変えた模擬ヘッダーで検証したもので、元ゲーム試験とは区別する。
