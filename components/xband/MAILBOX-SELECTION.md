# メール保管と返送選択の部品仕様

## 役割の分離

1. ROM依存の入口は、登録要求と送信1Dを解析する。
2. `MailCaptureStore`は元の宛先・タイトル・符号化本文を保管し、同内容でも別IDを付ける。
3. `MailAccountRoutes`は登録されたコードネームを宛先へ照合する。重複名や未登録名は推測しない。
4. `selectMailbox`は宛先のメールから保持済みIDを除外し、返送する最大件数を選ぶ。
5. ROM依存の出口は、選ばれたメールを受信1Eに組み替える。UIは結果の観測値を表示するだけ。

2～4は`components/xband/include/xband`のC++20部品で、Ymir、Windows、ソケット、JSONに依存しない。
保存ファイルの入出力、登録要求、受信レコード形式、実験用トークンは外側のアダプターに残す。

## インターフェース

```cpp
MailboxSelection selectMailbox(
    const MailCaptureStore& store,
    const MailAccountRoutes& routes,
    const std::string& endpoint,
    std::span<const uint64_t> heldIds = {},
    size_t responseLimit = 4);
```

|項目|意味|
|---|---|
|endpoint|登録された接続先。電話番号や認証済みユーザーIDではない|
|heldIds|その要求で端末が保持を報告した保管ID。既読・配達完了ではない|
|matched|その宛先に一致した保管メール総数|
|withheld|保持済み報告に一致し、今回返送しない件数|
|prepared|返送候補の配列。実際の転送・ゲームへの表示は未保証|
|deferred|未保持だが返送上限を超えた件数。次回へ残す|

`matched = withheld + prepared.size() + deferred`。保持済みを除外してから上限を適用する。
例えば6通のうち先頭4通を保持、返送上限1なら、ID5を準備しID6を後回しにする。
上限を先に適用すると未受信のID5以降に到達できなくなるので禁止する。
重複したheldIdsは除外件数を二重に増やさず、未知IDは既存メールに影響しない。

部品は保管を削除せず、保持報告がない次の要求では再び候補になる。
戻り値のポインターは保管の要素を参照するため、保管を変更するまでだけ有効。
単一所有スレッドで選択とレコード変換を行い、UIには数値のコピーだけを渡す。

## 元ROMとの接続（現在は実験設定）

受信レコードのwordへ`0x1000 + localId`を入れ、次の登録要求のu16一覧から読む。
許容IDは1～128、トークンは0x1001～0x1080。`custodyIdsFromInventory`でuint64_tへ変換し、
上記部品へ渡す。範囲外は保持済み保管IDとして扱わない。
これは歴史的XBAND IDの解明ではなく、新規COW状態に限定した合成IDである。
サーバー再起動時はスナップショットからIDを復元し、番号を再利用しない。

## ステータス形式

既存`HOST_STATUS.host.endpoints[i].pb3_observation`に次を追加する。
旧キーは維持し、通信経路や要求／応答形式は変更しない。

```json
"mail_selection": {
  "matched": 8,
  "withheld": 2,
  "prepared": 4,
  "deferred": 2,
  "scope": "last_service_call",
  "receipt": false
}
```

最新のメール要求で準備した結果であり、全時間の累計でも配達済み件数でもない。
通話リセットで0へ戻る。UIの`held`は保持済み報告による除外、`later`は上限による後回し。
中央には保管件数・バイト数、`memory`か`snapshot-experiment`かを表示する。
スナップショット使用時に「RAM only」と表示していた旧表示は訂正する。
カードの状態は今回変更せず、報告がなければunknownのまま。

## 送信待ち消去：通常化できない理由

同日追加実測：元VF REMIXの同じプレイヤーで2通を作成し、561バイトの要求内に
既知の単件形式を連続した1D count2を確認した。これを根拠に、診断サーバーの受付を
プレイヤー0の0／1／2件へ限定拡張した。資源リストを長さでたどり、全要求の末尾まで
揃ってから一括保管へ渡す。容量不足・2件目の不正データ・保存失敗は部分保管しない。
2件要求では、既存の消去実験フラグを明示しても05を返さない。
他プレイヤー対応・通常消去・通常配布版は変更していない。
根拠は`outputs/ymir-xband-investigation/vf-mail-multiple-pending-20260929.md`、
今回の実装と検証は`outputs/ymir-xband-investigation/vf-mail-batch-admission-20260929.md`。
追加の原版試験では、2件を相手へまとめて返して一覧に表示し、本文7と987も確認した。
987は作成／受信画面の125画素が一致。診断メタデータによる限定転送であり、
恒久的な配達確認ではない。詳細は`outputs/ymir-xband-investigation/vf-mail-batch-body987-20260929.md`。

2026-09-29の追加解析：元1Dの生成もindex0～3を列挙している。
送信側と消去側の資源範囲0140～0143が静的に一致したため、全員分の要求を正しく保存し、
全件受付後だけ消去を検討する設計が候補になる。複数プレイヤーの実通信は未検証。
要求全件の内部一括受付`MailCaptureStore::retainBatch`を追加し、容量／不正データは
全拒否、ファイル保存成功後にのみRAM保管を公開するようサーバーを変更した。
ワイヤーパーサーの対応形式や通常起動の実験無効設定は拡張していない。
詳細は`outputs/ymir-xband-investigation/vf-mail-outgoing-scope-20260929.md`。

元ROMで確認した05／mask00000004は全4プレイヤーの送信待ちを処理する。
送信者やメールIDを渡す引数は、現在確認した経路にはない。サーバー側で保持IDを
選ぶだけでは、ROM側の消去範囲を狭められない。
現パーサーは観測済みプレイヤー0の0／1／2件だけを扱うので、全プレイヤーの保管完了を
保証できない。通常版への有効化はしない。実験フラグと既存の失敗時消去禁止を維持する。

次の解析は、全プレイヤー送信形式・全件受付条件、または選択的消去コマンドの有無。
未確認のビットを送る、ROMを書き換える、UIだけで受付成功に見せることはしない。
カード課金・認証、任意本文、アプリ終了後のモデム保存復元も今回の対象外。

2026-09-29追記：元VF REMIXで同じ端末のプレイヤー0／3の混在2件要求を実測した。
読み取り専用解析はPASSだが、ライブの混在保管・配送は未対応。
診断サーバーの非空プレイヤー0受付は、登録ヘッダーの現在プレイヤー番号候補も0の場合に限定する。
別プレイヤーの現在登録名をプレイヤー0の差出人へ誤付与しないためで、不一致は全件拒否、保管ID発行・消去なし。
この条件は認証ではなく保守的な拒否条件。空の受信要求は対象外で、通常配布版も未更新。
詳細は`outputs/ymir-xband-investigation/vf-mail-mixed-player-capture-20260929.md`。
