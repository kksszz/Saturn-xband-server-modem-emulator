# エミュレーター側接続アダプターの実装状況

## 2026-09-28更新：モデムコマンドの切断待ち

現在のYmirフロントエンドは、ゲームからのATZ／ATHを
`ModemServiceClient::requestClose(now)`へ渡します。処理中のopen／転送を
取り消して再送するのではなく、その1回の処理完了を待ち、旧応答を破棄して
closeを要求します。close_okでidleに戻るまでは、新しいopen／転送とゲストへの
旧CONNECT／応答を禁止します。UARTアクセスでソケット待ちは行いません。

これはモデムのコマンドによるリセットです。サターン全体のリセット、
ロードステートによる時刻巻き戻し、無効化、アプリ終了は引き続きstopで
接続を破棄します。実通信異常の自動復旧、再送、期限延長は追加していません。
Windows用接続所有者に実装してあり、Ymir固有の型への依存はありません。
移植先でもこの区別を保ち、stepを呼び続け、close完了後だけ次の発信を開始します。

詳細と検証範囲は
`../../outputs/ymir-xband-investigation/vf-mail-deferred-close-20260928.md`。
以下の初期記録の「リセット」は接続自体の破棄を指し、ATZ／ATHの最新経路とは
区別してください。実機の全リセット挙動が確認できたという意味ではありません。

## 2026-09-27更新：以下の初期実装記録との区別

下記は初期のEcho接続部品の記録である。その後PB3については、独立した2つの
実Ymirコアプロセスと別サーバーによる限定対戦再生まで確認した。通常Ymirの
UI統合、別PC間LAN試験、完全なモデム実装を意味しない。
最新の実装境界と証跡は `../../outputs/ymir-xband-investigation/modem-core-extraction-20260927.md`
および `ymir-modem-bus-migration-20260927.md` を参照する。
レジスターとAT解釈はエミュレーター側、ログイン応答のバイト状態機械はサーバー側に分離した。
PB3ログインはゲストPC/RAM監視なしで接続通知まで再確認済み。

## 現在の構成

```text
既存のYmir使用ゲーム試験ハーネス（変更なし）
  モデム → LocalServiceEndpoint → 同じプロセス内のLocalPPPProbe

今回追加した独立部品の試験経路
  ClientControl → フレーム化JSON → TCP → TcpHost / ServerSession
                                             ├ サービスの生成・解放
                                             └ status() → 監視用情報
```

`include/xband/client_control.hpp` のClientControlは、将来Ymir側から呼ぶ
接続制御の部品です。Ymirに依存しないため、他のエミュレーターでも同じコードを
利用できます。既存ゲーム経路をこの部品に切り替える変更はまだしていません。

## 実装済みの範囲

- helloでエンドポイント名・設定キー・clock_hzを送信し、サーバー発行のsessionを受領。
- openで自局電話番号を送り、対応するopen_okを受けて初めてservice状態へ遷移。
- サーバーからのpingにpongを返答。送信キューが満杯なら入力を保持し、後で再開。
- snapshotでカード状態のコピーと累計値を通知。call・subscriberは内部状態から設定。
- close / close_okで通話を解放し、callと電話番号を消去。
- data / data_ackでバイナリを送受信。1メッセージ最大4096バイト、受信保持は65536バイト。
- advance / advance_okで明示的なguest tickを通知し、サービス処理の完了を確認。
- 誤った返信番号・セッション、予期しない応答、期限切れでは接続を終了。

状態はhello → idle → opening → service → closing → idleです。
エラー・EOF・リセット時はstoppedとし、再接続では新しいオブジェクトを作ります。
サービス名は既存wire v2のlocal-serviceであり、ゲーム対戦相手への接続成立ではありません。

## 呼び出し契約

1. ソケット接続後に構築。nowはホストの単調増加ミリ秒で、ゲームのフレーム数ではありません。
2. 所有スレッドでpoll(now)を定期呼び出し。
3. output()の範囲を送信し、実際に送れたバイト数だけsent(n)で通知。
4. 受信したバイト列をfeed(bytes, now)へ渡し、consumed分だけ進めます。
   consumedが0なら未消費分を保持し、busy-waitせず後のpollで再開します。
5. EOFやソケットエラー時はdisconnect()。切断後の再利用・自動再送はしません。

全操作は所有スレッド限定です。ネットワーク待ち、ソケット生成、スレッド起動は
この部品の責務ではありません。送信キュー満杯時はqueue_fullを返し、ローカル要求を
受理しません。呼び出し側が後で再試行します。入力の不正や例外はfail-closedとし、
構築時の例外は呼び出し側で扱います。秘密キーをログに出力しないでください。

open/closeの応答期限は送信キュー登録から5秒。helloは構築から5秒です。
TCPが接続されただけでゲーム側へCONNECTを返してはいけません。今後のモデム
制御との対応付けで、サービス接続とゲーム対向接続を別々に扱う必要があります。

- 非同期TCPクライアントのYmirのモデム/UARTへの組み込み。
- 完全なXBANDサービス、実ゲームでの接続・対戦、別PC間のLAN検証。

現在はEcho試験用オブジェクトで接続制御とバイナリ転送を確認しています。
試験で表示された番号・度数は独立した固定データです。実カード台帳、ROM、BIOS、
ゲーム設定、配布済みEXEは変更しません。TLSも追加していません。

## データ・時刻API

1. `transmit(bytes, now)`でデータを送信待ちキューに登録します。
   queued以外なら受理されていないため、元データを保持してください。
   credit_fullは相手側の受信容量が不足、queue_fullは送信待ちキューが満杯です。
2. `advance(guest_tick, now)`で、それまでの送信データをサービス側で処理する時刻を通知。
   nowは接続監視用のホスト時刻、guest_tickはエミュレーター由来の時刻で別物です。
3. `advancing()`がtrueの間は次のtransmit・advance・通常closeを受理しません。
   ソケット送受信とpollは継続してください。中断が必要ならdisconnectで接続全体を破棄します。
4. `received()`が返す連続部分をモデム側へ渡し、実際に取り込めた数だけ
   `consumeReceived(count, now)`で消費します。消費分だけ相手へ追加受信容量を通知。
   バッファはリング構造なので、残り全体が1つのspanになるとは限りません。
5. advance_okのcall・reply_to・tickが一致したらadvancingがfalseになり、
   completedTickを更新します。返信データは完了応答より先に届く場合があります。
   受信容量を戻すため、応答待ち中もデータを取り込めるモデムアダプターが必要です。

受領ACKだけでは相手に追加容量を与えません。ゲスト消費が遅いと送信も止まります。
待ちが5秒のadvance応答期限を超える場合は接続を破棄します。別の通知で期限を延長しません。
送受信オフセットはcallごとに0から開始し、close完了または切断で受信残データとともに消去。
完了済みtickより小さいローカル要求はinvalidで拒否し、通信には出しません。
同じtickの再指定は許可しますが、別のサービス処理要求として扱います。

これはゲームの同期スケジューラーやUARTバイト到着時刻の再現そのものではありません。
実ゲームへ接続する前に、これらとYmirのクロック・停止・リセットの対応付けが必要です。

## Windows用の非同期TCPクライアント

`include/xband/windows_tcp_client.hpp` のTcpClientを追加しました。
ClientControlを内部に所有し、Winsockの非ブロッキングソケットへ接続します。
共有の`xband::windows_tcp`ターゲットをリンクして利用します。
Ymir・GUI・カード台帳への依存はなく、TLSやWindowsサービスも追加しません。

ClientConfigの指定項目:

| 項目 | 意味 |
|---|---|
| server_address | IPv4の接続先。既定は127.0.0.1 |
| port | 必須のTCPポート（1～65535） |
| allow_lan | 既定false。trueの場合のみRFC1918のプライベートIPv4も許可 |
| endpoint | サーバーへ登録したモデムの識別名 |
| key | 登録と一致する64文字の小文字16進キー。平文で送信される |
| clock_hz | エミュレーターの時刻単位。1～1,000,000,000の整数 |

DNS名、0.0.0.0、公開IPv4、別の127.xアドレスは受理しません。
LANの相手は自PCのアドレスではないため、ホストのbind時とは異なり自PCの
インターフェース一覧との一致は要求しません。この制限は暗号化・相手の真正性・
LAN内攻撃対策を提供するものではありません。キーをパスワードと共用しないでください。

呼び出しは、構築→定期的なstep(now)→stopの順です。
stepは待ち時間ゼロのselectと非ブロッキング送受信を使い、内部にSleepや
ネットワーク待ちループを持ちません。1回の送信は最大4096バイト、受信保持も
4096バイト、フレーム処理は最大4回です。未処理の末尾は次回へ保持します。
これはOS呼び出しやメモリー確保まで含めたリアルタイム実行時間保証ではありません。

control()が非nullならClientControlへアクセスできます。ただしhello中の場合も
あるので、openはidleになってから行ってください。stop・失敗を起こしたstep・
デストラクターの後は、以前取得したポインターを使用してはいけません。
stepとcontrolへの操作はすべて同じ所有スレッドに限定します。

TCP接続試行は構築から5秒、helloはTCP接続完了から別途5秒で期限切れになります。
期限はホストの単調増加時刻で判定します。ゲストを停止してもstepを呼び続ける
必要があります。実際にどのスレッドから呼ぶかはYmir統合時の課題です。
EOF・ソケットエラー・プロトコルエラー・時刻逆行時はソケットと接続状態を破棄。
自動再接続や未確認データの再送はしません。再接続は新しいインスタンスで行います。

この段階の確認はlocalhostのみです。実TCPで4096バイトのバイナリ往復、
アイドル時のheartbeat、サーバー停止の検出、キー不一致、hello期限切れ、
ホスト時刻逆行、接続先ポリシーを試験します。LAN許可の判定は試験しますが、
別PCへの接続や実ネットワーク上の接続試行タイムアウトは未検証です。

## フレーム単位サービス呼び出しとの境界

`remote_service_batch.hpp`のRemoteServiceBatchは、既存pumpService呼び出しを
非同期通信へ置き換える際の共通部品です。Ymir固有のクロック取得は行いません。
現在のxband_dual_boot.cppでは、stepFrame内でローカルPPPサービスを直接呼び、
続いてRunFrameしています。この順序をネットワーク経由でも守る必要があります。

```text
1. モデムから集めたデータ＋処理対象guest tickをbeginで固定
2. TCPのstepを実行 → batchのresumeを実行（完了まで繰り返す）
3. doneを確認 → エミュレーターが次の区間へ進む
```

beginは最大65536バイトを内部へコピーします。trueなら元の入力バッファを
変更しても今回の処理に影響しません。falseなら受理していません。
送信キューへの登録位置を保持し、advanceは1回だけ登録します。
resumeのsinkは、モデム側が1バイトを受け取れたらtrue、受け取れないなら
副作用なしでfalseを返します。取り込めた分をまとめて消費・受信容量通知します。
例外や接続不整合はfailedとし、効果が不明なデータを再送しません。

進行状態はidle/progress/blocked/done/failedです。blockedでもTCPのstepは
継続します。doneを受け取るまでは次のフレームを実行せず、同じbeginも繰り返しません。
cancelはサーバーに届いたデータを取り消せないため、ClientControl全体を切断します。
再接続・リセット時には新しい接続とバッチオブジェクトを用意します。

この部品が使うClientControlは排他的に扱い、他の呼び出し元から同時に
transmit/advance/consumeReceivedを行わないでください。ClientControlはバッチより
長生きする必要があります。TcpClientのstepがfalseを返した後はcontrolへの参照が
無効になるため、batchのresume/cancelを呼ばず、バッチを破棄してください。

Ymirの公開APIを確認したところ、RunFrameは実行サイクル数を返しません。
既存のSetExecutionBudgetCallbackも対戦ケーブル用の変更が入っているため、
無条件に上書きしてモデムへ転用していません。guest tickの取得・区間境界・
ポーズ中も通信を処理する場所は、今後のYmir統合で明示的に決める必要があります。
現段階では、ゲーム試験ハーネスのローカル経路を変更していません。

## 実Ymirコアでの時刻・実行待機試験

独立した`outputs/live-capture-tests/xband_remote_core_test.cpp`を追加しました。
既存のゲーム試験用EXEではなく、この試験専用Saturnインスタンスにだけ
SetExecutionBudgetCallbackを設定します。対戦ケーブル用のコールバックを
上書きする変更はありません。Ymir本体のソース変更も今回ありません。

`GuestExecutionGate`はコールバックで得たスケジューラーのcycle・revisionと、
GetClockRatiosのmasterClock×masterClockNum/masterClockDenを使います。
開始時のcycleを原点とし、経過サイクルを整数演算でナノ秒へ切り捨て変換します。
各区間の丸め値を加算せず、原点から再計算するため丸め誤差は蓄積しません。
GUI FPSや実時間をゲスト時間の代用にしません。

```text
Ymirスケジューラーのcycle・revision・クロック比
    ↓ GuestExecutionGate（guest tick = ナノ秒）
区間末端でRunFrameがyieldし、ゲストを保持
    ↓ RemoteServiceBatch → TcpClient → 試験Echoサーバー
応答を取り込み、doneを確認
    ↓ release()で次の4096サイクルを許可
```

命令実行の小さな超過は実測cycleに含めます。超過64サイクルという試験上の
安全上限を超えた場合は停止します。64は実機命令の厳密な最大値ではありません。
保持中のcycle変化、逆行、revision変更、クロック比変更、算術のオーバーフローは
古い通信時刻と混ぜずに失敗扱いとします。クロック比の動的切替への継続対応は未実装です。

試験はRAMに置いたオリジナルSH-2ループを実行します。BIOS・ディスクは不要です。
8区間それぞれで実TCPの応答待ち中にRunFrameを繰り返し、cycleが増えないことと、
完了後の再開、バイナリの一致を確認します。最後に実際のSaturn::Resetを実行し、
revision変更を検出して待機・切断へ移ることを確認しました。

ビルドと実行（プロジェクトルートから）:

```powershell
cmake --build outputs/live-capture-tests/build --config Release --target xband_remote_core_test --parallel 2
.\outputs\live-capture-tests\build\Release\xband_remote_core_test.exe
```

既存のローカルYmirビルドにリンクする専用ターゲットです。
これはモデムのUART、ゲームのPPP、2台対戦、別PC間LANの動作確認ではありません。
実ゲームへの切替前には、それらとの結合とクロック切替時の扱いを追加する必要があります。

## 診断UARTとの接続口（2026-09-27）

`Probe` に明示的な任意コールバックを追加しました。通常は未設定なので既存の
ローカル経路を使用します。`diagnosticServiceTransmit` はデータモードの送信を
受け付け、`diagnosticServiceCarrier` はDCD表示、`diagnosticServiceHangup` は
切断通知を担当します。コールバックの参照先は所有者が寿命を管理してください。
`receiveServiceByte` は256バイトの診断RXキューに空きがある場合だけ追加し、
受信時刻を通知します。満杯なら副作用なしでfalseを返します。

`xband_remote_uart_test` は既存UARTレジスタ関数を直接呼び、LCP要求をTCPの
サーバーに送り、PPP応答をRXレジスタから読み出します。DLAB設定時の書き込みが
送信されないこと、RX満杯時の保留・再開、LSR/IIR、切断後のDCDとバッファを検査します。
これはSH-2が命令でUARTを操作する試験ではなく、AT/ログイン完了も明示的に省略します。
SCU割り込み配送、ボーレート、エスケープ制御、ゲーム用サービスは未結合です。

重要：この段階の試験はRX満杯時にテスト側がレジスタを読んで空きを作ります。
ゲスト実行を完全停止したままRXキューの空きを待つ実装はデッドロックし得るため、
先の実行ゲートとの単純結合は不可です。実ゲームへの適用前に、有限の受信待機領域と
ゲストへ渡す時刻・再開条件を設計し、双方が待ち続けないことを検証します。
MMIO送信を受け付けられない場合は例外で停止します。黙って破棄・再送はしません。

```powershell
.\outputs\live-capture-tests\build\Release\xband_remote_uart_test.exe
```

## 受信待ちとゲスト停止の分離（2026-09-27）

`StagedServiceBatch` は `RemoteServiceBatch` の応答を、UARTとは別の最大64 KiBの
リングバッファに取り込みます。通信完了まではUARTへ公開せず、`advance_ok` と
応答取り込みが完了したら `readyToRun()` がtrueになります。UARTが満杯でも
この許可は取り消されません。呼び出し側は決められたゲスト時刻で `drain()` を
呼び、受け付けられた分だけUARTへ渡してゲストを再開できます。

- `begin()` 成功から通信完了まではゲスト再開不可。通信は別途 `TcpClient::step()`
  で進めます。途中の応答はUARTへ流しません。
- `drain()` は既定256バイトまで。UARTが拒否したら、そのバイト以降を保持します。
  未配達分が残っていても次のバッチを開始でき、受信順序を維持します。
- 保管容量を超えたら接続を終了し、未配達分と再開許可を消します。無制限の蓄積や
  満杯のままゲスト停止を維持する処理はしません。容量は実機FIFO仕様ではありません。
- 切断・リセット時は必ずアダプターを破棄します。`TcpClient::step()` が失敗すると
  参照先が破棄されるため、以後 `resume`/`drain`/`cancel` を呼んではいけません。
- これはバイト保管と許可状態の部品です。CPU実行ゲートを自動操作せず、ボーレートや
  配達時刻をエミュレートしません。実ゲームへはまだ適用していません。

UART試験を更新し、RXが256バイト満杯のままで通信が完了し、再開許可が出ることを

## 実SH-2命令との結合試験（2026-09-27）

## AT接続・切断の限定アダプター（2026-09-27）

`ModemCallControl` は正規化済みのATコマンドを受け取り、新しいプロトコルの
`open` / `close` とモデム応答を対応付けます。完全なATパーサーではありません。
本人の電話番号（subscriber）とダイヤル先サービス番号は別々に設定します。
許可するダイヤル先は設定値との完全一致だけで、実電話網への発信はありません。

| 操作 | 動作 |
|---|---|
| AT | OKを返す |
| ATDT番号 / ATS91=15S92=15DT番号 | 設定されたサービス番号ならopenを要求 |
| open受付待ち | CONNECTを出さず、DCDもオフ |
| open_ok受信 | DCDオン、CONNECT 14400を1回だけ返す |
| ATH0 / ATZ / ATZ0、通信バッチ待ちなし | DCDオフ、close_ok後にOK |
| 接続受付中・通信バッチ待ち中の切断 | 接続全体を終了し、遅れてCONNECTを出さない |
| 異なる番号 | NO CARRIER、openを送らない |

`14400` は既存診断用の応答文字列であり、実効ボーレートの実装を意味しません。
ATZはここでは通話終了のみ扱い、UART・設定プロファイルのリセットは呼び出し側の
責務です。接続全体を終了した場合は、新しいTCP接続とアダプターが必要です。
`+++` のガード時間・コマンドモードへの移行はこの部品にはありません。

応答文字列は256バイトで上限を設け、UART側が受け取った分だけconsumeします。
切断時は呼び出し側がUART、送信待ち、StagedServiceBatchもクリア・破棄してください。
TcpClient失敗後に無効になったClientControl参照へpollしてはいけません。

更新したUART試験では、実際にAT文字列をUARTへ書いて新しい通話制御へ渡し、
open_ok後にCONNECTをUARTから読み出します。ログインはまだ省略したPPP限定試験です。
既存HELO/login/Password処理はゲームのブレークポイントや状態フラグに依存しており、
そのまま一般的な認証プロトコルと見なして移植はしていません。次は受信バイト列に
基づくログイン状態遷移の抽出と、受信配達タイミングの検証が必要です。

## VF限定の診断用ログイン部品（2026-09-27）

`tools/diagnostic_login_endpoint.hpp` を追加しました。根拠は既存の
`xband_vf_dual_boot.cpp` と `vf-xband-login-notes-20260926.md` です。
PB3のアドレス依存ブレークポイントとは異なり、VF用の既存試験には受信バイト列で
ユーザー名を確認する処理があり、この限定プロファイルを独立させています。

| 段階 | 診断用条件と応答 |
|---|---|
| 開始 | 最初のCRを受信するとHELO |
| 待ち | ゲスト時間で60フレーム後にlogin: |
| ユーザー名 | Pstrn + LFとの完全一致でPassword: |
| パスワード相当 | 8バイトとLFを消費。内容を保存・照合しない |
| PPPへ移行 | 次の0x7Eから既存PPP処理へ渡す |

60フレームは既存診断用の待ち時間で、実サービスの要件とは未確認です。
パスワード相当の8バイトは安全側の試験条件として0x21～0x7Eに限定しています。
これは過去の実サービスが受理した全文字集合を示すものではありません。
8バイト+LFという長さは既存観測によりますが、認証成功を意味しません。
成功応答の捏造、カード残高変更、アカウント照合は行いません。

不一致、順序違反、時刻逆行は汎用エラーで終了し、資格情報をエラーに含めません。
プロンプトは32バイト以内で保持し、パスワード文字列は保持しません。
ただし下位TCP転送バッファまで秘匿・消去を保証する実装ではなく、TLSもありません。
試験では合成した値だけを使用し、実パスワードの入力用途には使用しないでください。

実TCP試験はナノ秒→試験用60Hz変換、待ち時間直前/直後、ユーザー名の分割、
パスワード行とPPP要求の同一バッチ受信を検査し、PPP応答を従来処理と比較します。
追加の試験で異常入力・部分受信後のリセットも確認します。
この部品はまだゲームランチャーや通常サーバーに組み込まず、明示的な試験だけで
使用しています。実ゲームとの再接続検証と他タイトルへの適用範囲は未確認です。

## ゲスト時間による受信間隔の制御（2026-09-27）

`GuestBytePacer` はUART直前に1バイトだけ保持します。渡されたゲスト時刻に
明示的な配達間隔を足した時刻まで配達せず、UARTが拒否すればその1バイトを保持します。
ホストの実時間は参照しません。遅れて呼ばれても過去の空き時間をクレジットとして
蓄積せず、次のバイトは改めて間隔を空けるため、一度に大量配達しません。
時刻逆行・時刻加算の桁あふれ・sink例外は停止、resetは未配達バイトを破棄します。

SH-2ログイン試験ではCONNECTとログイン/PPP応答をこの共通経路へ通します。
固定の694445ナノ秒は「14400 bit/s、1バイト10ビット」と仮定した切り上げ値です。
実機仕様や現在のUART分周器・データ長設定を検証して算出した値ではありません。
配達は4096サイクルの区間境界に丸められるため、正確なボーレート再現とは異なります。

この固定間隔でログイン試験は6800実行区間・65バッチ・70受信バイトで成功し、
配達間隔が下限を守ること、全受信内容がRAM上で一致することを確認しました。
次はUART設定との対応と実ゲームの限定試験です。既存ゲーム用EXEは変更していません。

## UART設定からの受信間隔計算（2026-09-27）

上記の固定間隔試験を拡張し、`uart16550CharacterNanoseconds` に入力クロック、
DLL、DLM、LCRを渡して1文字分の所要時間を計算します。これは明示的に選ぶ
16550系の診断モデルであり、サターンモデムの搭載チップを同定したものではありません。
参照仕様は [TI TL16C550Cデータシート](https://www.ti.com/lit/ds/symlink/tl16c550c.pdf)
のボーレート生成器とLCRです。

- 分周値は `DLL + 256 × DLM`、ビット速度は `入力クロック ÷ (16 × 分周値)`。
- 文字長は開始1ビット、データ5〜8ビット、任意のパリティ1ビット、停止ビットの合計。
  停止ビットはLCRに応じて1、1.5（データ5ビット時）、2です。
- 時間はナノ秒へ切り上げます。クロック未指定・分周値0・未対応のbreak状態は
  値なしを返し、呼び出し側で停止などを判断します。勝手なクロック補完はしません。
- `GuestBytePacer::setPeriod()` は次に預かるバイトから適用します。
  すでに預かったバイトの期限は変更しません。これは診断用の更新方針です。

SH-2試験コード自身がDLL=8、DLM=0、LCR=3（8N1）を設定します。
試験側が明示する1,843,200 Hzでは14,400 bit/s、1文字694445 nsになります。
このクロック値は実機測定値ではなく、試験条件です。本番の既定値にはしていません。
2回の実行とも6800区間・65バッチ・70受信バイトが一致し、全134件の部品試験も通過しました。

配達は依然として4096サイクル境界です。ビット波形、パリティエラー、SCU割り込み、
実ゲームの通信成功や実機のクロック源まで確認できたという意味ではありません。
既存ゲーム用EXE、ディスク、BIOS、カード残高は変更していません。

### 通信途中のUART設定変更

`xband_remote_cpu_login_test --change-uart` ではCONNECT応答の1バイト目を読んだ後、
ゲストSH-2命令で分周値8/LCR=0x13から分周値16/LCR=0x1fへ変更します。
2バイト目が受信間隔制御部に保持されていることを必須条件として検査します。
そのバイトは元の期限を保ち、後続は新しい間隔になります。各バイトの受付時刻と
受付時の間隔を記録し、早すぎる配達や、保持中バイトへの新間隔の遡及適用を検出します。

この試験は7203区間・68バッチで完了し、70バイトすべてがRAM上で一致しました。
通常・低速の固定設定試験も再実行して成功しています。ただし設定レジスタの複数回の
書き込みが実行区間境界をまたぐ途中状態や、実機の設定変更中のビット波形は未検証です。
本番モデム設定・配布用EXEへの変更はありません。
