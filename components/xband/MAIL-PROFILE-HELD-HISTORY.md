# 保持確認履歴による再配信抑止（診断用）

## 背景と変更

元VF REMIXで返信を受信→再接続→削除→再接続すると、削除した同じ保管ID3が再配信された。従来は「今回報告された保持ID」しか除外しないため、削除で報告されなくなると候補に戻る。

新しい明示設定 `XBAND_MAIL_PROFILE_REMEMBER_HELD_EXPERIMENT=1` では、以前提示したIDを、その宛先のゲームが後の完全な要求で保持報告したときだけ記憶する。同じ端末・試験実行範囲・プレイヤーに対して、そのIDを以降の候補から除く。

- **提示だけ**：再配信できる。応答を準備しただけで受信完了にしない。
- **後の接続で保持を実測**：履歴へ追加し、現在の一覧からなくなっても再配信を抑止する。
- **別の端末／実行範囲／プレイヤー、未知／未提示ID**：履歴を借用しない。
- **外側の接続切断・範囲無効化**：提示表と保持履歴を両方破棄する。

これは現在の診断モードにおける再配信ポリシーであり、実XBANDの削除コマンドを解析したとの主張ではない。保持リストからの不在を削除と確定していない。クライアントの保存消失・リスト変更でも、確認済みIDを再配信しなくなる点に注意。

## 移植用API

`include/xband/mail_profile_offers.hpp` の `rememberedHeldFor(target, reportedIds)` が、検証済み保持の履歴を含む除外ID一覧を返す。従来のconst `heldFor` は今回報告分だけを返し、変更していない。

履歴は提示表の容量以内、標準C++20のみ。不正なターゲットや上限超過を検証してから一括更新する。Ymir、Windows、GUI、ソケットに依存しない。`invalidateAll()` で提示と履歴をまとめて無効化する。

サービスは完全なmail-only要求の既存解析後に、このAPIを選択する。保管メール自体は削除しない。送信箱消去・保存形式・カード残高・相手決定・通信同期は変更しない。

## 設定と表示

既定OFF。controlled profile inventoryが必須で、設定不足時は起動を拒否する。試験ラッパーの `-RememberHeld` は環境変数を明示設定し、終了時に元へ戻す。未指定時は継承した環境変数を試験中だけ解除する。

`XBAND_MAIL_PROFILE_HELD_HISTORY` に `current`（今回確認した保持数）／`remembered`（履歴を含む除外数）を別々に出力する。通常inventoryログのvalidated／withheldは履歴を含む。したがってreportedよりwithheldが多くても、現在の受信件数が増えたという意味ではない。

永続化・正式な配達／読了ACK・認証・exactly-onceは未実装。現在の通常配布版や既存返信パッケージは更新していない。

2026-09-30の追加試験で、元VF REMIXの両機を維持したままサーバーのみ再起動すると、保管3件の復元後にID1/3を再提示し、削除済みメールがゲームの一覧に復活することを確認した。再起動耐性は未実装。詳細は `../../outputs/ymir-xband-investigation/vf-mail-restart-regression-20260930.md`。

同日の後続修正で、明示的な `-DeleteTrial -RestartTrial` 診断に限り、宛先名・提示ID・保持確認履歴のスナップショットを追加した。元ゲームで再起動後も該当行は空のまま。詳細は `../../outputs/ymir-xband-investigation/vf-mail-restart-fixed-game-20260930.md`。上記「永続化は未実装」は通常モードに関する記述であり、この限定診断では状態を保存・復元する。
